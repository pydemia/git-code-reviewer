# 대형 PR 묶음 분석 실행 기록

## 구현 범위

기존 PostgreSQL job·lease·checkpoint와 snapshot artifact를 확장했다. 별도 broker나 provider framework는 추가하지 않았다.

- Git 변경 목록은 NUL 형식으로 전부 읽는다. 2,000파일 절단을 제거했고 rename의 이전·현재 경로와 탭·개행·Unicode·pathspec 문자를 보존한다.
- 50파일 이상 또는 기존 전체 diff byte 예산을 넘는 Skill 분석에는 묶음 경로를 사용한다. 일반 PR은 기존 경로와 128회 호출 예산을 유지한다.
- 전체 manifest, 일반 묶음과 경계 검토 작업, 입력 hash, 시도 횟수, 상태, 검증된 응답을 저장한다. 작업 완료에는 모든 target ID 응답, JSON·등급·분류·코드 위치 검증이 필요하다. 누락·잘림·잘못된 anchor를 완료 처리하지 않는다.
- Python/JS import, SQL table, 파일 경로 참조를 정적 연결 후보로 사용한다. 주 작업은 모든 변경 window를 담당하고 경계 작업은 관련 계약·table의 변경 문맥을 함께 검토한다. 해석되지 않는 경계는 endpoint 전체 문맥을 보수적으로 제공한다.
- 모델 입력은 기본 64KB의 묶음 본문과 별도의 고정 prompt/source/output 여유로 제한한다. 큰 window를 분할하고 분할할 수 없는 단일 입력은 `blocked`로 기록한다. 파일별 별도 LLM 요약은 없으며 채택한 의견으로 파일 요약과 계층식 PR 요약을 만든다.
- 계정 공통 RPM·byte 제한과 호출 ledger는 유지한다. 묶음 동시성은 1로 시작해 성공 8회마다 늘어나며 등록 provider 상한과 4 이내에 머문다. 실패 시 낮추고 429의 유효한 Retry-After를 줄이지 않는다. 5xx는 cooldown 후 재시도하며 대기 중 worker 슬롯을 반환한다.
- rate/capacity 대기는 최대 50회·24시간까지 crash retry와 구분해 저장한다. 개별 분석의 호출·시간 예산은 별도로 유지한다. 다른 계정이나 모델로 우회하지 않는다.
- 새 `남은 검토 재개`는 기존 보고서를 보존한 새 revision을 만든다. refresh 권한, 개인 메모리 소유자, 현재 PR base/head, 활성 저장소를 확인한다. 같은 입력 계획으로 검증된 묶음만 재사용한다. 중복 클릭은 같은 revision을 반환한다. 발행 억제 분석에서 시작한 재개는 발행 억제를 보존한다.
- UI는 기존 진행 영역·command button·디자인 토큰을 재사용한다. 검토 파일 수와 묶음 완료 수, 정책상 제외, 대기·실패 상태를 구분한다. 의견 없는 파일 목록을 다시 노출하지 않는다. reference-led-frontend와 agent-skills의 frontend-development 지침을 적용했다.

## 사용자가 요청한 호출 예산 조정

128회는 API 사업자의 제한이 아닌 GCR의 소프트웨어 예산이다. 대형 PR의 기본 예산을 **512회 / 3시간**으로 늘린다. 일반 PR 128회와 chat 예산은 유지한다.

- runtime: `ANALYSIS_GROUP_MAX_MODEL_CALLS=512`, `ANALYSIS_GROUP_MAX_DURATION_MS=10800000`.
- Helm: `model.analysis.groupMaxModelCalls`, `model.analysis.groupMaxDurationMs`.
- 동일 분석의 재시작은 ledger를 초기화하지 않는다. 새 revision을 명시적으로 재개하면 표시된 추가 예산을 부여한다.
- 계정의 실제 quota와 Retry-After를 넘겨 강제 호출하는 설정이 아니다. 기록한 token 수는 UTF-8 byte 기반의 보수적 추정과 출력 여유이며 공급자의 실제 usage가 아니다.

## 검증 근거

- 실제 HTTPS Git 저장소와 NUL manifest 검사: 2,107파일, 탭·개행 rename, literal pathspec, 잘린 목록 거부.
- analysis-engine·Git·source context·Chrome 회귀 119건 통과. 후속 예산/UI 검사 12건 통과. 서로 겹치는 테스트가 있으므로 합산 수치로 보고하지 않는다.
- 격리 PostgreSQL의 기존 Skill/memory·장애 복구·admission·task store 26건 통과. 추가 real worker → artifact/report → API 검사는 합성 transport를 사용해 60파일을 3묶음과 요약 1회로 완료했다. 실제 모델 판단 증거가 아니다.
- worker 중단 후 검증된 task 재사용, stale lease 쓰기 거부, 입력 hash 변경 거부, 개인 분석의 다른 사용자 재개 차단, 현재 head 검사, 중복 재개, 2시간 Retry-After와 lease 반환을 검사했다.
- Chrome 1360px/420px에서 상태·추가 예산·reader 버튼 숨김·키보드 Enter·실패 표시·가로 넘침을 검사했다. screenshot은 합성 상태임을 파일명에 명시했다.
- runtime/web typecheck, ESLint, production build 통과. 기존 Vite bundle 크기 경고는 유지된다.

## 실제 실행 경계

사용자가 GCR 호출 예산 증액을 요청했다. 등록된 #1024 분석의 provider·모델·reasoning을 유지하고 고정 snapshot의 새 revision에 최대 512회·3시간 예산을 사용한다. 기존 보고서와 계정 설정은 변경하지 않고 GitHub 댓글 게시를 억제한다. 자동으로 무제한 예산을 추가하지 않는다. 결과·실제 ledger 수·배포 source/digest는 실행 후 아래에 기록한다.

## 남아 있는 제한

정적 연결은 lexical hint이며 완전한 AST·동적 호출 그래프가 아니다. 변경되지 않은 모든 호출부를 찾는 검색, 임의의 큰 단일행/context 413에 대한 자동 계획 재편성, 공급자별 실제 token usage 수집은 완료했다고 주장하지 않는다. oversized 입력은 blocked/실패로 남겨 운영 설정·계획을 조정해야 한다. Prompt·Skill·메모리 내용이 바뀌거나 만료·철회되면 이전 결과를 섞어 완료 처리하지 않는다. 재개가 필요한 경우 새 revision을 사용한다.

LP01의 무절단 목록·내구성·명시적 재개, LP02의 bounded lexical 그룹·coverage, LP03의 admission·durable wait·동시성 조절, LP04의 요약·진행·재개 UI를 구현했다. LP05의 실제 모델 결과와 배포 후 검증은 별도로 확인하며 전체 계획 완료로 선기록하지 않는다.
