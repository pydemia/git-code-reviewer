# 대형 PR 묶음 분석 실행 기록

## 구현 범위

기존 PostgreSQL job·lease·checkpoint와 snapshot artifact를 확장했다. 별도 broker나 provider framework는 추가하지 않았다.

- Git 변경 목록은 NUL 형식으로 전부 읽는다. 2,000파일 절단을 제거했고 rename의 이전·현재 경로와 탭·개행·Unicode·pathspec 문자를 보존한다.
- 50파일 이상 또는 기존 전체 diff byte 예산을 넘는 Skill 분석에는 묶음 경로를 사용한다. 일반 PR은 기존 경로와 128회 호출 예산을 유지한다.
- 전체 manifest, 일반 묶음과 경계 검토 작업, 입력 hash, 시도 횟수, 상태, 검증된 응답을 저장한다. 작업 완료에는 모든 target ID 응답, JSON·등급·분류·코드 위치 검증이 필요하다. 누락·잘림·잘못된 anchor를 완료 처리하지 않는다.
- Python/JS import, SQL table, 파일 경로 참조를 정적 연결 후보로 사용한다. 주 작업은 모든 변경 window를 담당하고 경계 작업은 관련 계약·table의 변경 문맥을 함께 검토한다. 해석되지 않는 경계는 endpoint 전체 문맥을 보수적으로 제공한다.
- 모델 입력은 기본 64KB의 묶음 본문과 별도의 고정 prompt/source/output 여유로 제한한다. 큰 window를 분할하고 분할할 수 없는 단일 입력은 `blocked`로 기록한다. 파일별 별도 LLM 요약은 없으며 채택한 의견으로 파일 요약과 계층식 PR 요약을 만든다.
- 계정 공통 RPM·byte 제한과 호출 ledger는 유지한다. 묶음 동시성은 1로 시작해 성공 8회마다 늘어나며 등록 provider 상한과 4 이내에 머문다. 실패 시 낮추고 429의 유효한 Retry-After를 줄이지 않는다. 5xx는 cooldown 후 재시도하며 대기 중 worker 슬롯을 반환한다.
- rate/capacity 대기는 최대 50회·24시간까지 crash retry와 구분해 저장한다. 개별 분석의 호출·시간 예산은 별도로 유지한다. 다른 계정이나 모델로 우회하지 않는다.
- 새 `남은 검토 재개`는 기존 보고서를 보존한 새 revision을 만든다. refresh 권한, 개인 메모리 소유자, 현재 PR base/head, 활성 저장소를 확인한다. 같은 입력 계획으로 검증된 묶음만 재사용한다. 중복 클릭은 같은 revision을 반환한다. 발행 억제 분석에서 시작한 재개는 발행 억제를 보존한다.
- UI는 기존 진행 영역·command button·디자인 토큰을 재사용한다. 검토 파일 수와 묶음 완료 수, 정책상 제외, 대기·실패 상태를 구분한다. 의견 없는 파일 목록을 다시 노출하지 않는다. reference-led-frontend와 agent-skills의 frontend-development 지침을 적용했다.

## 사용자가 요청한 호출 예산 조정

128회는 API 사업자의 제한이 아닌 GCR의 소프트웨어 예산이다. 대형 PR의 기본 예산을 **512회 / 3시간**으로 늘린다. 일반 PR 128회와 chat 예산은 유지한다.

- runtime: `ANALYSIS_GROUP_MAX_MODEL_CALLS=512`, `ANALYSIS_GROUP_MAX_DURATION_MS=10800000`.
- Helm: `model.analysis.groupMaxModelCalls`, `model.analysis.groupMaxDurationMs`.
- 동일 분석의 재시작은 ledger를 초기화하지 않는다. 새 revision을 명시적으로 재개하면 표시된 추가 예산을 부여한다.
- 계정의 실제 quota와 Retry-After를 넘겨 강제 호출하는 설정이 아니다. 기록한 token 수는 UTF-8 byte 기반의 보수적 추정과 출력 여유이며 공급자의 실제 usage가 아니다.

## 남아 있는 제한

정적 연결은 lexical hint이며 완전한 AST·동적 호출 그래프가 아니다. 변경되지 않은 모든 호출부를 찾는 검색, 임의의 큰 단일행/context 413에 대한 자동 계획 재편성, 공급자별 실제 token usage 수집은 완료했다고 주장하지 않는다. oversized 입력은 blocked/실패로 남겨 운영 설정·계획을 조정해야 한다. Prompt·Skill·메모리 내용이 바뀌거나 만료·철회되면 이전 결과를 섞어 완료 처리하지 않는다. 재개가 필요한 경우 새 revision을 사용한다.

LP01의 무절단 목록·내구성·명시적 재개, LP02의 bounded lexical 그룹·coverage, LP03의 admission·durable wait·동시성 조절, LP04의 요약·진행·재개 UI를 구현했다. LP05의 실제 모델 결과와 배포 후 검증은 별도로 확인하며 전체 계획 완료로 선기록하지 않는다.

## 진행 화면 보정과 운영 절차

실제 화면에서 묶음 상태가 탭의 고정 높이에 끼어 잘리는 문제를 발견했다. 상태 영역을 기존 진행 표시 아래로 옮겼다(`81887f9`). 파일 coverage도 diff를 파싱한 수 대신 검증된 파일 완료 수로 계산하도록 바꿨다(`5a481f9`). 미완료 파일이 남은 1,043/1,045를 반올림해 100%로 표시하지 않으며, 파일 완료 수가 없는 구형 보고서는 `—`로 표시한다. 기존 26/1,045 보고서는 2%다.

이 보정은 report/browser 회귀 5건, web typecheck·build·ESLint, 운영 API를 읽는 전체 화면 검사로 확인했다. 배포 전 전체 화면 검사에는 로컬 build와 Playwright의 읽기 전용 API 중계를 사용했다. 처음 로컬 HTML만 교체한 검사에서는 브라우저의 `net::ERR_FAILED`로 API를 읽지 못했으며 통과 처리하지 않았다. 배포 후 직접 접속 검사는 별도로 남긴다. 모든 임시 로그인은 finally에서 로그아웃했다.

alpha.70/chart 0.10.66과 alpha.71/chart 0.10.67은 화면 보정으로 만들었지만 운영에 배포하지 않았다. 실제 429 처리 결함을 확인한 뒤 해당 보정도 포함하는 alpha.72/chart 0.10.68을 준비했다. 실행 중 요청이 없는 queued 시점에 분석을 잠시 보류하고 배포한다.

- 분석 화면의 `묶음 검토 완료/전체`는 검증된 작업 수다. 파일은 연결된 일반·경계 검토가 모두 끝나야 완료된다. 제외 파일은 완료 수에 포함하지 않는다.
- 진행 중 rate limit 대기는 저장된 작업과 동일한 호출 ledger로 다시 이어진다. 작업을 새로 만들거나 예산을 초기화하지 않는다.
- `partial`/`failed` 보고서에 미완료 작업이 남았을 때 refresh 권한 사용자는 `남은 검토 재개`를 사용할 수 있다. 화면에 표시된 추가 예산으로 새 revision을 생성한다. 같은 base/head·계획·입력·고정 문맥의 완료 결과만 재사용한다. head 변경이나 권한·자료 유효성 문제는 먼저 해결해야 한다.
- Helm의 `model.analysis.groupMaxModelCalls`와 `groupMaxDurationMs`는 대형 분석의 개발 설정이다. API 사업자의 quota나 계정 공통 admission을 변경하지 않는다. 기본값은 512회와 10,800,000ms(3시간)이며 일반 분석 128회는 유지한다.
- 이번 #1024 검증 revision은 게시를 억제했다. 이 revision에서 수동 재개해도 게시 억제를 유지한다. 본 작업에서 외부 PR 댓글은 게시하지 않는다.

01:35:51 UTC부터 실제 HTTP 429를 관측했다. worker stack의 배포된 `model-admission.js:111`을 확인해 429 처리 분기에서 발생했음을 대조했다. 5xx나 단순 로컬 동시성 대기라고 추정하지 않았다. 첫 세 번은 같은 크기의 입력 86,840 bytes였으며 호출 ledger에 failed 3건, 작업에는 `retry-wait`가 남았다. 동시성은 4→2→1로 줄었고 지정된 cooldown까지 job lease를 반환했다. 완료 92개 작업은 유지됐다. 이는 개발 예산 512회와 별개인 외부 한도이며 다른 계정·모델로 우회하지 않았다.


반복 429 확인 후 01:40:11 UTC 해당 analysis job이 queued이고 진행 중 원격 요청이 없는 시점에 `available_at`만 15분 뒤로 옮겼다. 분석 ID·예산 ledger·완료 task·계정 설정은 바꾸지 않았다. 이 시점까지 완료 작업 92개, 완료 HTTP 응답 93개, 429 실패 7개, DB 장애 중 interrupted 1개였다. HTTP 완료는 task 검증 완료와 다른 수치다.

`e8f5582`에서 429의 bounded 응답 본문(16KiB/1초)에서 알려진 `usage_limit_reached`의 `resets_at`/`resets_in_seconds`만 읽도록 보완했다. 원문 오류 메시지·토큰·요청 내용은 보관하지 않는다. HTTP Retry-After와 본문 reset 중 더 늦은 시각을 사용하고 최근 account ledger의 연속 실패에 따라 30초에서 최대 15분까지 backoff를 늘린다. 공급자가 알려준 더 긴 시각은 줄이지 않는다. 오류 형식은 [OpenAI Codex의 공개 응답 테스트](https://github.com/openai/codex/blob/main/codex-rs/codex-api/src/endpoint/responses_websocket.rs)의 `usage_limit_reached`/`resets_at` 사례도 대조했다.

0057 migration은 ledger에 안전한 failure metadata(HTTP 상태, 허용된 코드, 재시도 시각)만 추가한다. 초기화가 분석 deadline보다 늦으면 추가 모델 호출 없이 미완료 보고서를 남긴다. parser 5건, task/admission DB 16건과 후속 account/chat 회귀 25건이 통과했다. 이 수치에는 중복 테스트가 포함되며 합산하지 않는다. 단위·회귀 응답은 합성이고 실제 공급자 body 확인은 배포 후 같은 분석을 이어서 수행한다.
