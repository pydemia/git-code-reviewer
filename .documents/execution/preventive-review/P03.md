## C04: GCR에서 Keycloak 사용자 관리

관리자 사용자 탭에 조직 계정 생성·명시적 기존 계정 연결·초대 메일·비밀번호 재설정 메일을 추가했다. Server와 Worker의 `IDENTITY_ADMIN_ENABLED` 기본값은 false다. GCR은 기존 사용자 ID·subject·역할·tenant·리뷰 이력을 유지하고 Keycloak은 credential을 관리한다. 설정·최소 realm 권한·관리 속성·재시도 절차는 [운영 계약](../../../docs/operations/keycloak-user-administration.md)을 따른다.

Additive migration 0034는 provider binding·request fingerprint·dispatch marker를 기존 operation/outbox에 추가한다. 동일 요청은 하나의 작업으로 처리하고 생성 응답 유실은 정확한 사용자명과 세 관리 속성을 모두 확인해 복구한다. 새 앱/IdP 계정은 비활성으로 만들며 명시적 연결과 remote readback 뒤 앱을 활성화한다. 이메일 자동 연결·OIDC subject 덮어쓰기·로컬 credential 생성은 없다.

Worker는 2분 lease와 `SKIP LOCKED`, 활성 관리자 재확인, 늦은 완료 차단을 사용한다. 메일은 네트워크 호출 전에 dispatch marker를 저장하며 결과 불명 작업은 재발송하지 않는다. 재설정 요청은 먼저 앱 세션·freshness를 폐기하고 security epoch를 증가시킨 뒤 Keycloak 전체 세션 종료와 메일을 실행한다. GCR 차단·삭제는 진행 중인 계정 작업을 supersede한다. 일반 API로 연결된 비활성 사용자를 직접 활성화할 수 없으며 확인된 재활성화와 IdP 직접 변경 수집은 C05에서 구현한다.

## C03: 앱 SAML 인증과 로그아웃

`AUTH_MODE=saml`에서 `/auth/login`과 `/auth/saml/login`, POST ACS, 서명된 metadata, Redirect SLO를 등록한다. LoginPage는 서버의 인증 방식이 확인된 후 조직 계정 로그인 링크 또는 local form을 표시한다. SAML 설정·trust metadata를 확인하지 못하면 startup 또는 인증을 거부하며 다른 인증 방식으로 자동 전환하지 않는다. 설정 계약과 운영 제한은 [SAML 앱 인증](../../../docs/operations/saml-web-authentication.md)에 정리했다.

C01 프로토콜 검증을 `apps/runtime/src/auth/saml-protocol.ts`로 옮겼다. 기존 script는 이 구현을 재사용하는 shim이다. Node-SAML 5.1.0의 Redirect parameter 탐색은 opaque RelayState 안의 `SigAlg` 같은 문자열을 잘못 선택했다. 재현 fixture를 추가하고 protected parameter extraction hook만 exact-key 방식으로 교체했다. 서명 검증·인증서 처리는 같은 library에 맡기며 Signature 필수·RSA-SHA256·중복/추가 parameter 거부를 유지한다.

로그인은 임의의 RelayState별 `__Host-` transaction cookie와 DB의 nonce hash를 함께 요구한다. 성공하면 해당 cookie만 제거하고 `Secure; HttpOnly; SameSite=Lax`인 `gcr_session`을 발급한다. SessionNotOnOrAfter와 최대 8시간 중 짧은 만료를 적용하며 매 요청에서 사용자·identity 상태, security epoch·freshness를 확인한다. Freshness를 확인하지 못하면 `503 IDENTITY_UNAVAILABLE`로 응답한다. 일반 변경 API의 Origin 검사는 유지하고 정확한 POST ACS만 예외로 둔다.

일반 로그아웃은 해당 NameID/SessionIndex에 속한 앱 세션을 즉시 폐기한다. 다른 SessionIndex의 세션은 보존한다. IdP LogoutRequest와 SP LogoutResponse의 서명·destination·issuer·request/browser binding을 검증하고 DB에서 일회성으로 소비한다. Additive migration 0033은 폐기한 SessionIndex를 10분간 보관해 로그아웃 전에 시작한 AuthnRequest의 늦은 응답이 세션을 다시 생성하지 못하게 한다. 로그아웃 뒤 새로 시작한 요청은 다시 인증할 수 있다.

검증 결과:

- [전체 source 검증](evidence/P03-C03-source.json): Node 22.23.2, 103개 test file의 861개 test가 실패·skip 없이 통과했다. 전체 typecheck·build·lint와 변경 source의 format도 통과했다. 전체 format 검사는 기존의 무관한 Markdown 5개를 지적하며 해당 문서는 변경하지 않았다.
- [공통 계약 fixture](evidence/P03-C03-contract-node22.json): 기존 44개 악성/정상 서명 계약을 새 공통 protocol로 재검증했다. 추가 IdP LogoutRequest fixture 26개는 전체 suite에 포함된다.
- [앱·DB 검증](evidence/P03-C03-source.json): 실제 서명과 PostgreSQL로 두 앱 instance의 단일 소비, 다중 탭, nonce·returnTo·CSRF, session expiry/freshness, SessionIndex별 SLO, 지연 응답, DB 실패의 원자적 rollback, static 오류 응답, 실제 Pino log의 query/cookie 비노출을 검사했다. 이전 C02의 별도 Node process replay 회귀도 [다시 통과](evidence/P03-C03-state-replicas-node22.json)했다.

Native Safari와 실제 운영 SAML 전환은 검증하지 않았다. 시험에서는 실제 서명에서 확인한 persistent NameID를 관리 함수로 fixture 사용자에 명시적으로 연결하고 fixture에만 provisioning/freshness를 부여했다. 운영 provisioning·상태 수집·공유 DB ACL·companion chart·복구/전환은 C04–C08에서 진행한다.

## C01: SAML library와 Keycloak 계약

`scripts/saml-contract.mjs`는 앱에 등록되지 않은 검증용 SP다. Node-SAML을 이용해 AuthnRequest·LogoutRequest를 만들고 서명된 로그인·로그아웃 응답을 검증한다. XML 서명·canonicalization을 직접 구현하지 않는다. 앱에 연결할 때 이 검증 조건을 유지하고 메모리 transaction ledger를 P03-C02의 DB transaction으로 교체해야 한다.

| 항목 | 검증한 값 |
| --- | --- |
| SP library | `@node-saml/node-saml@5.1.0`, root devDependency exact pin |
| XML signature | `xml-crypto@6.1.2`, exact pin |
| XML parser | wrapper `@xmldom/xmldom@0.9.12`, Node-SAML·xml-crypto 내부 `0.8.15` lock |
| Keycloak | 공식 `26.7.3`, `quay.io/keycloak/keycloak@sha256:ff4257d0d64efbe99ed1ddfaf07765cc3c36dc7518bf8324d41961327f441c54` |
| PostgreSQL | 실제 `17.11`, `postgres@sha256:18cfe3ef5e6815560c98237d6216d1e5119702fb0f3894c8785dd58b8bbe5d73` |
| 환경 | macOS arm64, Node `22.23.2`, 설치된 Chrome `152.0.7977.84` headless, Playwright `1.63.0` |
| Binding | 서명된 Redirect AuthnRequest → POST Response, 서명된 Redirect SLO request/response |
| 알고리즘 | RSA-SHA256·SHA256 digest·exclusive canonicalization, Response와 Assertion 모두 서명 필수 |
| 신원 | persistent NameID, 존재하는 NameQualifier·SPNameQualifier는 각각 정확한 IdP·SP 값과 비교 |
| 시간·크기 | transaction 최대 5분, skew 최대 60초, assertion 최대 age 5분, XML/압축 해제 최대 128 KiB |

2026-09-13 확인한 [Node-SAML 보안 공지](https://github.com/node-saml/node-saml/security/advisories/GHSA-4mxg-3p6v-xgq3)는 5.1.0에서 검증된 XML로부터 assertion을 읽도록 수정했다고 명시한다. [Keycloak 26.7.3 릴리스](https://www.keycloak.org/2026/08/keycloak-2673-released)와 [공식 DB 지원 표](https://www.keycloak.org/server/db)의 PostgreSQL 17.x 지원도 확인했다. 이 선택은 영구적인 보안 보증이 아니며 P03 운영 전환·릴리스 때 공지를 다시 확인한다.

### 라이브러리 기본값을 보완한 조건

로그인에서는 issuer, Destination, Recipient, 두 InResponseTo, bearer SubjectConfirmation, AudienceRestriction, 시간과 SessionIndex를 명시적으로 검사한다. DTD·entity 선언·comment/CDATA·복수 assertion·중복 ID·다른 서명 대상·약한 알고리즘을 거부한다. 신원은 `getAssertionXml()`의 검증된 assertion에서만 읽는다. XML 원문과 library error를 외부 응답에 넣지 않는다.

Node-SAML 5.1.0의 Redirect SLO 검증에는 Signature가 없을 때 성공 경로가 있고 metadata 생성기는 SLO POST binding을 고정한다. Wrapper는 Signature·RSA-SHA256·중복 없는 정확한 query parameter를 먼저 요구하고 bounded inflate 이후 library 검증을 호출한다. SP metadata는 구현한 Redirect SLO binding으로 생성한 후 xml-crypto로 서명한다. 이미 서명한 문서를 고쳐서 내보내지 않는다. Metadata의 실제 서명·ACS POST·SLO Redirect는 fixture에서 검증했다. 근거는 [Node-SAML source](https://github.com/node-saml/node-saml/tree/v5.1.0/src)와 설치한 동일 version의 코드다.

Library cache의 get/remove는 원자적인 replay 차단이 아니다. PoC는 browser nonce에 결합된 한 request만 보이는 읽기 view를 library에 주고 모든 검증 후 transaction·Response ID·Assertion ID를 함께 소비한다. 이번 ledger는 단일 process의 `Map/Set`이므로 replica 간 race·crash·재시작 보장은 P03-C02에서 DB로 검증한다.

### 검증 결과

- [Node 22 계약 fixture](evidence/P03-C01-contract-node22.json): 44개 통과. 정상 서명, issuer/audience/recipient/destination·시간·NameID 변조, wrapping·중복 ID·복수 assertion·XXE·크기, 서명 키 overlap/철회, 같은 process의 replay 경쟁, SLO signature/parameter/압축 제한을 검사했다.
- [최종 Node 22 실제 Keycloak](evidence/P03-C01-keycloak-macos-node22-attempt2.json): 로그인 3회와 각 SLO 완료. 서로 다른 site인 `gcr.sp.test`와 `keycloak.idp.test` 사이의 HTTPS POST에서 `Secure; HttpOnly; SameSite=None` host-only transaction cookie가 전달됐다. 일반 session cookie는 `SameSite=Lax`이고 SLO 뒤 제거됐다. 다음 로그인에는 credential 재입력이 필요했다.
- 같은 임시 사용자의 이메일·표시 이름을 Admin API로 바꾼 뒤 persistent NameID와 Keycloak user ID가 유지됐다. 새 RSA signing key를 활성화하고 승인한 metadata의 두 certificate로 로그인했으며 이전 certificate만 신뢰한 검증은 새 키의 응답을 거부했다.
- Keycloak 자체가 unsigned AuthnRequest와 등록하지 않은 ACS 주소의 서명된 request를 400으로 거부했다. 사용한 SAML Response를 HTTPS ACS로 재전송해도 400이며 새 session을 만들지 않았다.
- 임시 TLS leaf의 SPKI만 Chrome test process에 pin했다. `ignoreHTTPSErrors`는 false이며 별도 unpinned certificate는 실제 Chrome에서 `ERR_CERT_AUTHORITY_INVALID`로 거부됐다. Node HTTPS도 명시한 certificate로만 신뢰한다. 시스템 trust store는 변경하지 않았다.
- 기존 runtime auth/config 회귀 17개, 새 script ESLint, frozen-lockfile offline 설치 통과. 새 SAML/XML/browser dependency의 `pnpm audit` advisory는 없었다. 전체 workspace에는 기존 `@fastify/static` 4건(high 1, moderate 3)과 Vitest/mocker 2건(moderate)이 남아 있으므로 다음 서버 배포 전에 수정·회귀 검증한다.

### 실패 기록과 검증 한계

첫 [실행](evidence/P03-C01-keycloak-macos.json)과 [진단 실행](evidence/P03-C01-keycloak-macos-attempt2.json)은 로그인 submit을 `input`으로만 찾는 harness 때문에 실패했다. Failure page title에 생성된 AuthnRequest URL이 포함될 수 있어 원문 title은 기록하지 않고 page category·transport error code만 보존한다. 해당 실패 증거에서도 URL이 들어 있던 title을 제거하고 진단 설명을 남겼다.

매 실행은 임시 realm·계정·인증서·DB container·Docker network를 만들었고 성공/실패 모두 자신이 만든 container·volume·network·파일을 제거했다. 테스트의 bootstrap master admin은 임시 환경만 구성하며 GCR runtime service account 모델을 대신하지 않는다. 실제 운영 계정·원래 앱 DB·기존 Docker volume·OS keychain에는 변경이 없다.

Headless Chrome 결과를 Safari·사용자가 보는 GUI 검증으로 확대하지 않는다. IdP-initiated SSO는 client에 활성화하지 않았으며 IdP-initiated logout, 앱 route의 CSRF·multi-tab·SessionNotOnOrAfter, 명시적인 기존 사용자 mapping, DB replay, identity freshness, 공유 DB ACL, optimized companion image, DNS/TLS/SMTP와 운영 전환은 P03-C02–C08에 남아 있다.

## C02: SAML transaction과 명시적 신원 연결

`0032_saml_identity_state.sql`은 기존 사용자·subject·credential·권한·개인 memory owner를 수정하지 않고 다음 저장 구조를 추가한다.

- `user_identities`: 기존 app user와 persistent NameID·qualifier·issuer·SP 및 Keycloak user ID의 명시적 연결. Provisioning 상태·검증 시각·security epoch·최대 5분 freshness를 저장한다.
- `saml_transactions`: 최대 5분 AuthnRequest/LogoutRequest, provider 설정 hash, RelayState·browser nonce hash, 내부 return path와 일회성 소비 시각. Logout 필드는 한 묶음으로 존재해야 한다.
- `saml_message_consumptions`: configuration과 message ID hash의 unique ledger. Response·Assertion·Logout message는 같은 ID namespace를 사용하며 보존 시간은 10분이다.
- `user_sessions`의 nullable SAML binding: identity·user의 composite FK, SessionIndex·security epoch·SessionNotOnOrAfter. 기존 session의 새 필드는 모두 null이며 SAML session은 최대 8시간과 assertion session 만료 중 이른 시각을 따른다.
- `identity_admin_operations`·`identity_admin_outbox`: 명시적인 관리 작업·중복 방지·claim/retry/delivery 상태. Password·token·임의 JSON payload column은 없다. 실제 Admin API processor는 C04/C05에서 구현한다.

`apps/runtime/src/auth/saml-state.ts`의 신원 연결 API는 활성 administrator와 대상의 기존 OIDC subject를 확인한다. 연결은 pending·disabled로 생성하며 로그인이나 이메일 일치로 사용자를 만들거나 연결하지 않는다. 같은 Keycloak account를 다른 app user에 붙이거나 기존 사용자의 identity를 덮어쓰는 요청은 거부한다. 이 구현에서는 issuer 내 Keycloak account당 하나의 app user mapping을 허용한다. 여러 SP 간 공유 정책이 필요하면 별도의 명시적 변경이 필요하다.

로그인 시작 시 새 request ID·RelayState·browser nonce를 생성하고 DB에는 nonce/state hash만 보관한다. `loadSamlLogin`은 provider·browser에 결합된 미소비 transaction만 protocol verifier에 보여준다. `consumeSamlLogin`의 입력은 이미 서명·protocol 검증을 마친 신원이며 XML을 파싱하거나 서명을 대신 검증하지 않는다. C03에서 C01 verifier와 연결해야 한다.

소비 시 transaction, user, identity 순서로 잠그고 활성 사용자·검증된 identity·freshness를 검사한다. Response/Assertion hash 삽입, session hash와 binding 저장, transaction 소비를 한 DB transaction에서 commit한다. Unique 충돌이나 storage 오류가 나면 전부 rollback한다. 관리자의 사용자 차단과 같은 user lock을 사용하며 lock 대기·저장 도중 deadline이 지났는지도 마지막에 다시 확인한다. DB error detail과 token 원문은 오류에 첨부하지 않는다. Session을 만들 때 freshness를 연장하지 않는다.

`pruneSamlState`는 만료된 transaction과 message hash만 batch별로 정리하고 다른 transaction이 잠근 행은 건너뛴다. C01의 assertion 최대 age 5분·skew 1분보다 긴 message 보존 시간을 전제로 한다. 실제 route와 정리 작업 등록은 C03 이후 단계다.

### 검증

Node 22.23.2에서 새 33개를 포함한 **전체 767개 테스트가 실패·skip 없이 통과**했다. 공통 package·runtime·web build, runtime typecheck, 새 TypeScript 파일 ESLint도 통과했다. [전체 source 검증](evidence/P03-C02-source.json)과 [두 process 실행 증거](evidence/P03-C02-replicas-node22.json)에 결과와 source hash를 기록했다.

임시 PostgreSQL 17.11에 migration 31개와 기존 사용자·로컬 credential·session·repository grant·tenant membership·개인 memory fixture를 먼저 만든 뒤 0032를 적용했다. 기존 row와 ID·subject·role·group·owner가 그대로이며 pending identity를 연결해도 바뀌지 않았다.

별도 Node process 두 개와 서로 다른 PostgreSQL backend PID로 같은 응답을 동시에 소비했다. 하나만 성공했고 새 session 1개·소비 transaction 1개·message hash 2개가 남았다. 서로 다른 사용자·AuthnRequest가 같은 Response ID를 동시에 쓰는 경우도 하나만 성공했다. 새 DB pool에서 이전 응답을 재전송하면 거부한다.

Nonce·RelayState·request ID·provider·login/logout 종류 불일치, request/session 만료, 비활성·삭제 사용자와 pending·비활성·stale·미래 검증 identity를 거부했다. 별도 탭의 유효한 요청은 독립적으로 성공한다. Message ID의 다른 종류 재사용, 잘못된 session owner FK, 5분을 넘는 freshness와 불완전한 logout binding도 거부했다. DB trigger로 저장 오류와 freshness 만료를 재현해 session·소비 기록이 함께 rollback되는 것을 확인했다. 실제 user row lock 대기를 관찰한 관리자 차단 경합에서도 대기 중인 로그인이 거부됐다.

이 검증의 신원 입력은 합성된 verifier 출력이다. 실제 Keycloak 서명·HTTPS browser callback 증거는 C01과 구분하며, 앱의 실제 SAML callback·Safari/Chrome·CSRF·로그아웃·운영 provisioning/revocation은 C03–C08에 남아 있다. 현재 운영 인증은 local이며 배포 전후 DB 보존 검증은 C02 release 기록으로 추가한다.
