## C07 세 번째 checkpoint: GCR SAML Helm 연결

GCR chart에 `auth.saml`과 `identity` schema·validation, server/worker 전용 identity ConfigMap·관리 credential mount·egress, server 전용 SP key/certificate·metadata pin을 연결했다. SAML server는 기존 auth Secret에서 `SESSION_SECRET` key만 선택해 읽는다. Migration Job·wait init·retention·source-sandbox container에는 새 identity credential이나 ConfigMap을 전달하지 않는다. Sidecar는 worker와 network namespace를 공유하므로 container별 네트워크 차단을 구현했다고 표시하지 않는다.

Local auth 상태의 계정 provisioning/연결을 허용하고, SAML 전환에는 admin/security 수집 둘 다 활성화, 공유 DB role/TLS 격리, legacy Keycloak off, 명시적 issuer/admin network peer, 자동 tenant 가입 off를 요구한다. Master realm, 다른 realm의 관리 URL, 다른 origin의 SP Entity ID, 비정규 URL·잘못된 image digest, Secret 공유와 빈 peer를 거부한다. 외부 Secret/metadata 교체 시 소비하는 server/worker만 재시작하도록 revision annotation을 추가했다.

SAML/identity 활성화 시 앱의 pool 예산도 terminating Pod를 포함하도록 검사한다. 예시는 server/worker 각 1 replica·pool 6·peak 3과 retention 2로 총 38개를 기존 app role 한도 42 안에 둔다. 기존 bundled DB를 사용하는 TLS overlay와 합성해도 PostgreSQL 하나만 render되며 최초 설치의 일반 migration Job과 upgrade hook 구분을 유지한다. 실제 replica·drain·부하는 운영 전환 전에 재확인해야 한다.

[검증 기록](evidence/P03-C07-saml-chart.json): Helm 구성/거부/기존 모드 비교 55개, 합산 NetworkPolicy의 허용·거부 판정 72개, Node 22.23.2의 compiled 설정·SAML loader 시나리오 16개가 통과했다. 승인 metadata pin/URL 모드, local preparation, custom Entity ID, 실물 RSA key/certificate와 불일치·pin 유실 거부를 확인했다. URL mode 응답은 fixture이며 실제 IdP HTTPS·SAML browser 흐름은 아니다. 기존 DB chart 회귀 26개, runtime TypeScript build, 변경 JS ESLint/format도 통과했다. 개발·local·OIDC·proxy의 install/upgrade manifest는 `5b694de`와 같았다.

현재 source용 SAML 예시의 image digest/tag는 비워 둔다. 기존 alpha.37 image에는 C06 연결 격리 코드가 없으므로 현재 runtime을 검증·게시한 새 digest가 필요하다. Verifier와 API dry-run은 synthetic image reference를 사용한다. 리소스 17개의 strict server dry-run을 통과했고 실제 자원을 만들지 않았다. Runtime/SQL source, 실제 GCR/identity release·DB·Secret·HTTPRoute는 변경하지 않았다.

[설정·전환 절차](../../../docs/operations/saml-web-authentication.md#helm-설정과-전환-준비)에 peer 양쪽 정책, 기존 CA 유지, metadata/key revision, shared DB의 소유권 보존과 검증 한계를 적었다. Compose overlay, optimized Keycloak 실제 두 replica 검증과 image/Helm 게시, 운영 DNS/TLS/SMTP·DB role 전환, C08 mapping/복구, Commit Defender native UI·게시와 P04–P13은 남아 있다. 이 checkpoint는 C07 전체 완료나 운영 SAML 전환이 아니다.

## C07 두 번째 checkpoint: companion Helm chart

`deploy/helm/gcr-identity`를 추가했다. 기존 공유 PostgreSQL의 `gcr_keycloak`과 identity DB를 사용하며 PostgreSQL dependency·realm import Job·자동 Secret 생성을 포함하지 않는다. Optimized image의 repository/digest와 public/private HTTPS origin, DB·TLS Secret/CA, proxy·server/worker·DB peer를 환경에서 명시해야 render할 수 있다. 기존 GCR chart와 운영 release는 변경하지 않았다.

Public Service `git-code-reviewer-identity:80`은 적용된 HTTPRoute 계약을 유지한다. 관리 HTTPS Service 443과 management 9000을 나누고 proxy에는 Pod HTTP 8080만, GCR server/worker와 지정한 관리 peer에는 HTTPS 8443만 허용한다. Cache 7800/57800은 같은 namespace/release Pod끼리 허용하며 DNS·DB·선택 SMTP 이외 egress는 닫는다. Namespace/Pod selector의 AND 조건을 사용하고 빈 peer·전체 주소 CIDR를 거부한다. 이것은 정책 명세의 범위이며 CNI enforcement나 Gateway의 path/header 차단을 검증한 결과는 아니다.

UID/GID 1000·read-only root·capability 제거·ServiceAccount token 비자동 mount, 2 replica·anti-affinity·PDB, 분리된 startup/readiness/liveness와 graceful shutdown을 설정했다. 종료 중인 Pod가 surge 상한에서 제외될 수 있어 기본 peak allowance는 `2 desired + 1 surge + 2 terminating = 5`, pool은 `1/1/6`이다. `5 × 6 = 30`으로 C06의 role connection limit을 유지하고 scale·pool 변경이 예산을 넘으면 거부한다. 한 번의 rollout을 위한 allowance이며 동시 rollout·node 단절까지 Pod 수를 절대 제한하는 설정은 아니다.

[검증 기록](evidence/P03-C07-companion-chart.json): Helm 4.1.3의 lint·schema 음성 사례·Secret/TLS/Service/probe/rollout 연결 검사 44개와 네트워크 규칙 허용/거부 판정 250개가 통과했다. Install/upgrade가 같은 manifest를 만들며 선택 bootstrap·outbound CA·monitoring·SMTP, 외부 IPv6 DB/custom port, 명시적 scale 예산도 검사했다. 초기 verifier는 Helm 3의 dotted 오류 경로를 가정해 Helm 4의 JSON Pointer 오류 표현과 불일치했다. 두 표현을 지원한 뒤 원인 일치 검사를 통과했다. 명세 6개는 PRISM-DEV API의 strict server dry-run을 통과했으며 실제 resource를 만들지 않았다.

Chart·검증 script·운영 문서와 DBA 예시의 Keycloak pool 구성을 변경했다. DBA 예시는 `3 × 10`에서 `5 × 6`으로 바꾸되 role 연결 한도 30과 전체 예산은 유지한다. Image registry 게시, 두 replica 실제 Keycloak 보존/교체·SAML·NetworkPolicy·SMTP, Compose overlay와 GCR SAML Helm 연결, 공유 DB 운영 전환·C08 복구는 미완료다. Public HTTPRoute는 Service 미배포로 계속 `BackendNotFound`다. 현재 script의 offline 성공이나 dry-run을 C07 전체 완료·운영 SAML 전환으로 처리하지 않는다.

## C07 첫 checkpoint: optimized image와 인증 HTTPRoute 준비

공식 Keycloak 26.7.3 digest를 고정한 `deploy/identity/Dockerfile`을 추가했다. PostgreSQL·health·metrics를 build 단계에서 활성화하고 non-root `start --optimized`로 실행한다. Build context는 Dockerfile만 포함하며 credential·realm data를 넣지 않는다. ARM64 local image 빌드는 통과했다. 초기 무제한 JVM build는 중단하고 build heap 768 MiB·processor 2개를 명시한 빌드를 완료했다. 배포 대상 amd64 image 검증·registry 게시는 아직 수행하지 않았다.

실제 공유 DB와 Keycloak을 사용하는 runtime 검증 script를 준비했다. 첫 실행은 앱 migration 36개와 실제 Keycloak schema 생성, UID/GID 1000·read-only root·전용 DB role·TLS, `${...}$`가 들어간 literal password 및 database/cluster readiness를 확인한 후 테스트용 관리자 요청의 5초 제한에 걸렸다. 다음 실행은 관리자 요청에 30초를 적용했으나 초기 schema 단계에서 startup 경계를 넘었다. 세 번째 실행은 Keycloak 2 GiB·600초 startup 조건을 선택했지만 PostgreSQL 자체의 initdb가 기존 시작 제한 내에 끝나지 않아 Keycloak을 실행하지 못했다.

17:10 KST의 Mac은 physical memory 16 GiB, swap 사용량 27073.44 MiB, load average 20.80/39.58/49.37을 보고했다. 이를 시간 초과의 단일 원인으로 확정하지 않는다. 두 replica·사용자/서명 key 보존·DBA 재적용·TLS 음성 사례는 모두 **미완료**다. 세 실행의 소유 container·network·임시 credential 파일은 정리했다. [이미지와 검증 기록](evidence/P03-C07-optimized-image.json)은 성공한 build와 실패한 runtime 시도를 구분한다. Runtime·SQL source는 C06 checkpoint와 같다.

운영 사전 점검 시 Gateway는 HTTP 80·TCP 6333 listener만 제공했고 제안 identity hostname이 로컬에서 조회되지 않았다. 이후 사용자가 `/etc/hosts`를 등록하고 HTTPRoute 추가만 요청해 `git-code-reviewer-identity-route`를 적용했다. 해당 realm과 resources 경로를 향후 companion의 `git-code-reviewer-identity:80`으로 연결한다. `Accepted=True`지만 Service 미배포로 `BackendNotFound`이며 현재 realm 요청은 500이다. `/admin/`은 404, 기존 앱 health는 200을 확인했다. Route 변경은 `d2804ab`로 push했다. [적용 기록](evidence/P03-C07-identity-route.json)에 범위를 남겼으며 DB·Gateway listener·Helm release는 변경하지 않았다.

설계의 worker 관리 API 접근 제한은 C04/C05의 outbox·event collector 구현에 맞춰 수정했다. Service account는 server와 해당 worker에만 제공하고 migrator·retention·source sandbox에는 주지 않는다. Companion chart·Compose·TLS/서버 측 이름 조회·NetworkPolicy·복구/전환은 계속 구현해야 한다. C07 전체 완료 또는 운영 SAML 전환으로 처리하지 않는다.

VS Code 일반 창에 접근할 수 있는 상태는 확인했으나 CUA가 격리된 Development Host 대신 사용자의 기존 Code process를 선택했다. 전용 process만 종료하고 QA 디렉터리를 정리했다. 이 시도는 native UI 검증 통과가 아니며 기존 사용자 창의 파일·설정·credential은 수정하지 않았다.

## C06 세 번째 checkpoint: 운영 image의 볼륨 재사용

운영 PostgreSQL Pod의 시작 스크립트를 read-only로 확인하고 같은 amd64 image digest `e39896e0…`를 로컬에 내려받았다. 로컬 image의 `libpostgresql.sh` SHA-256 `ac83d1d7…`가 운영에서 읽은 파일과 일치했다. 운영 DB·PVC·Secret·release는 변경하지 않았다.

`verify-postgres-persistence.mjs`는 빈 DB와 기존 사용자·metadata·migration 36개가 있는 DB를 별도 Docker volume에서 검사한다. 2026-09-13 **16:15:30–16:21:54 KST**의 최종 실행에서 DB container 5개를 생성·교체했다. 기존 평문 DB를 같은 볼륨의 TLS container로 바꾼 후 빌드된 DBA CLI로 계정을 분리했다. 이후 다시 container를 교체하고 provisioning을 재실행해 앱/합성 identity 데이터, password verifier·role 속성·membership, DB/schema 소유권·권한 보존을 확인했다. Legacy NOLOGIN, 양방향 cross-DB 및 관리/template DB 접속 거부, 앱 DDL·ledger 쓰기 거부, 평문 TCP 거부도 재검사했다.

DB 서버와 인증서 복사 init은 UID/GID 1001·읽기 전용 root filesystem·capability 제거 조건에서 실행했다. 하위 chart의 본체/인증서 복사 image가 기본 `latest`를 쓰는 것을 확인해 격리 overlay에서 둘 다 검증한 PostgreSQL digest로 고정했다. Helm 검사 26개는 새 pin과 non-root init 설정 및 기존 기본 명세 보존을 확인한다.

첫 fixture 실행에서는 Docker가 비어 있는 named volume의 소유권을 image 기본값으로 덮어쓰는 것을 재현했다. Kubernetes fsGroup을 대신하는 소유권 준비 후 `volume-nocopy`로 mount해 수정했다. 다음 검사에서는 PostgreSQL의 null ACL과 명시적인 기본 owner ACL의 표현 차이로 비교가 실패했다. 권한 비교에 `acldefault` 정규화를 적용하고 default-ACL catalog OID를 제외했다. 이후 두 data fixture의 재시작·재실행 검사가 통과했다. 최종 non-root 인증서 복사 검사도 포함했으며 임시 container·volume·Secret 파일은 모두 정리했다.

[재현 절차](../../../docs/operations/shared-postgresql.md)와 [검증 기록](evidence/P03-C06-persistence.json)에 범위를 기록했다. Runtime/SQL source는 `da7e7c0`과 같으며 이전 940개 source 회귀 증거를 유지한다. 이번 변경은 검증 script·명시적 overlay pin·문서에 한정해 해당 실행·lint/format·Helm을 확인했다. 실제 운영 storage driver·backup restore, Keycloak realm/user/signing key의 보존, image/chart 게시와 운영 전환은 남아 있다.

## C06 두 번째 checkpoint: runtime TLS와 migration 권한 분리

`DATABASE_ISOLATED_ROLES=true`에서 앱·worker·retention은 `gcr_app`, 전용 migration command는 `gcr_migrator`로 접속한다. Migration credential이 없거나 불완전하면 앱 credential로 대체하지 않는다. 앱 command에는 migration 설정을 전달할 수 없다. CA chain과 DNS hostname/IP SAN을 검증하며 URL의 SSL·host·credential override를 거부한다. pg의 새 연결 callback에서 실제 role 속성·membership·소유권·cross-DB CONNECT·TLS·앱 DDL 및 ledger 권한·pool 한도를 검사한다. 이미 열려 있는 연결의 권한을 주기적으로 감사하는 기능은 아니다.

서버·워커 init container는 앱 권한으로 SQL 파일과 ledger checksum을 조회하는 `wait-migrations`만 실행한다. 전용 Job에만 migrator Secret을 mount한다. 번들 DB 최초 install은 일반 migration Job, upgrade는 pre-upgrade hook이다. 외부 DB는 pre-install/pre-upgrade hook이다. Chart에 별도 worker pool·rollout/종료 유예 budget·CA ConfigMap과 backend TLS 검사, 최종 상태 overlay 예시를 추가했다. 기본값의 기존 배포 명세는 그대로다.

Node 22.23.2에서 **105개 source 파일·940개 test가 실패·skip 없이 통과**했다. 기존 dist 중복 69개는 제외했다. 이 실행에는 빌드된 `migrate`·`wait-migrations`의 별도 process 검사와 실제 non-owner TLS server·worker 검사가 포함된다. PostgreSQL 18.6에서는 runtime TLS 8개와 DBA provisioning 14개, 합계 22개를 별도로 통과했다. Workspace typecheck/build, frozen lockfile, 변경 source lint/format, Helm 연결·실패 원인·기존 명세 보존 검사 26개도 통과했다.

초기 TLS fixture에서 IP 접속 시 드라이버가 localhost를 인증서와 대조하는 오류를 재현해 DBA와 앱 연결 모두 설정한 hostname/IP를 직접 검증하도록 수정했다. 추가 test 두 개의 suite 범위 오류도 수정했다. 병행 실행한 중간 검사에서는 기존 provisioning test 두 개의 30초 timeout이 있었으나 최종 전체 source와 별도 PG18 검사는 제한 시간을 늘리지 않고 통과했다. 이 결과로 시간 초과 원인 자체를 해결했다고 판단하지 않는다.

[검증 기록](evidence/P03-C06-runtime-connections.json)에 실행 시각·source/artifact hash·검사 범위와 미완료 항목을 기록했다. [운영 절차](../../../docs/operations/shared-postgresql.md)는 TLS backend 준비 → 연결 전환 → maintenance의 DBA provisioning → 역할별 앱 배포 순서와 Secret/CA 교체 후 재시작 조건을 설명한다. 이 checkpoint에서는 새 image·chart를 게시하거나 운영 DB·Secret·TLS를 변경하지 않았다. 실제 Bitnami persisted-volume 재시작과 Keycloak 공유 DB·복구 검증은 후속 적용 조건으로 남는다.

## C06 첫 checkpoint: 공유 PostgreSQL provisioning

2026-09-13 14:02:32 KST에 운영 DB의 metadata만 읽었다. PostgreSQL 18.6·max_connections 100·superuser 예약 3개이며 기존 `git_code_reviewer` login은 non-superuser지만 CREATEDB 권한과 DB/public 객체 소유권을 갖고 있었다. 확인한 앱 연결은 TLS를 사용하지 않았다. Role membership과 기존 default ACL은 없었다. 이 조사에서 운영 DB를 변경하지 않았다.

별도 DBA CLI를 추가했다. 관리 DB에서 read-only inspect 또는 명시적 apply를 실행하며 `gcr_app`·`gcr_migrator`·`gcr_keycloak`의 비밀번호 파일을 분리한다. 기존 DB와 비밀번호를 유지하고 legacy login은 NOLOGIN으로 퇴역시킨다. Database 소유자는 DBA, public schema/객체 소유자는 각 migrator로 두며 앱은 DML·sequence·function 실행과 migration ledger 조회만 허용한다. Management/template DB까지 PUBLIC CONNECT를 회수하고 실제 cross-DB CONNECT를 검사한다.

## C04: GCR에서 Keycloak 사용자 관리

관리자 사용자 탭에 조직 계정 생성·명시적 기존 계정 연결·초대 메일·비밀번호 재설정 메일을 추가했다. Server와 Worker의 `IDENTITY_ADMIN_ENABLED` 기본값은 false다. GCR은 기존 사용자 ID·subject·역할·tenant·리뷰 이력을 유지하고 Keycloak은 credential을 관리한다. 설정·최소 realm 권한·관리 속성·재시도 절차는 [운영 계약](../../../docs/operations/keycloak-user-administration.md)을 따른다.

Additive migration 0034는 provider binding·request fingerprint·dispatch marker를 기존 operation/outbox에 추가한다. 동일 요청은 하나의 작업으로 처리하고 생성 응답 유실은 정확한 사용자명과 세 관리 속성을 모두 확인해 복구한다. 새 앱/IdP 계정은 비활성으로 만들며 명시적 연결과 remote readback 뒤 앱을 활성화한다. 이메일 자동 연결·OIDC subject 덮어쓰기·로컬 credential 생성은 없다.

Worker는 2분 lease와 `SKIP LOCKED`, 활성 관리자 재확인, 늦은 완료 차단을 사용한다. 메일은 네트워크 호출 전에 dispatch marker를 저장하며 결과 불명 작업은 재발송하지 않는다. 재설정 요청은 먼저 앱 세션·freshness를 폐기하고 security epoch를 증가시킨 뒤 Keycloak 전체 세션 종료와 메일을 실행한다. ## C03: 앱 SAML 인증과 로그아웃

`AUTH_MODE=saml`에서 `/auth/login`과 `/auth/saml/login`, POST ACS, 서명된 metadata, Redirect SLO를 등록한다. LoginPage는 서버의 인증 방식이 확인된 후 조직 계정 로그인 링크 또는 local form을 표시한다. SAML 설정·trust metadata를 확인하지 못하면 startup 또는 인증을 거부하며 다른 인증 방식으로 자동 전환하지 않는다. 설정 계약과 운영 제한은 [SAML 앱 인증](../../../docs/operations/saml-web-authentication.md)에 정리했다.

C01 프로토콜 검증을 `apps/runtime/src/auth/saml-protocol.ts`로 옮겼다. 기존 script는 이 구현을 재사용하는 shim이다. Node-SAML 5.1.0의 Redirect parameter 탐색은 opaque RelayState 안의 `SigAlg` 같은 문자열을 잘못 선택했다. 재현 fixture를 추가하고 protected parameter extraction hook만 exact-key 방식으로 교체했다. 서명 검증·인증서 처리는 같은 library에 맡기며 Signature 필수·RSA-SHA256·중복/추가 parameter 거부를 유지한다.

로그인은 임의의 RelayState별 `__Host-` transaction cookie와 DB의 nonce hash를 함께 요구한다. 성공하면 해당 cookie만 제거하고 `Secure; HttpOnly; SameSite=Lax`인 `gcr_session`을 발급한다. SessionNotOnOrAfter와 최대 8시간 중 짧은 만료를 적용하며 매 요청에서 사용자·identity 상태, security epoch·freshness를 확인한다. Freshness를 확인하지 못하면 `503 IDENTITY_UNAVAILABLE`로 응답한다. 일반 변경 API의 Origin 검사는 유지하고 정확한 POST ACS만 예외로 둔다.

일반 로그아웃은 해당 NameID/SessionIndex에 속한 앱 세션을 즉시 폐기한다. 다른 SessionIndex의 세션은 보존한다. IdP LogoutRequest와 SP LogoutResponse의 서명·destination·issuer·request/browser binding을 검증하고 DB에서 일회성으로 소비한다. Additive migration 0033은 폐기한 SessionIndex를 10분간 보관해 로그아웃 전에 시작한 AuthnRequest의 늦은 응답이 세션을 다시 생성하지 못하게 한다. 로그아웃 뒤 새로 시작한 요청은 다시 인증할 수 있다.

## C01: SAML library와 Keycloak 계약

`scripts/saml-contract.mjs`는 앱에 등록되지 않은 검증용 SP다. Node-SAML을 이용해 AuthnRequest·LogoutRequest를 만들고 서명된 로그인·로그아웃 응답을 검증한다. XML 서명·canonicalization을 직접 구현하지 않는다. 앱에 연결할 때 이 검증 조건을 유지하고 메모리 transaction ledger를 P03-C02의 DB transaction으로 교체해야 한다.

| --- | --- |
| SP library | `@node-saml/node-saml@5.1.0`, root devDependency exact pin |
| XML signature | `xml-crypto@6.1.2`, exact pin |
| XML parser | wrapper `@xmldom/xmldom@0.9.12`, Node-SAML·xml-crypto 내부 `0.8.15` lock |
| Keycloak | 공식 `26.7.3`, `quay.io/keycloak/keycloak@sha256:ff4257d0d64efbe99ed1ddfaf07765cc3c36dc7518bf8324d41961327f441c54` |

[Keycloak 26.7.3 릴리스](https://www.keycloak.org/2026/08/keycloak-2673-released)와 [공식 DB 지원 표](https://www.keycloak.org/server/db)의 PostgreSQL 17.x 지원도 확인했다. 이 선택은 영구적인 보안 보증이 아니며 P03 운영 전환·릴리스 때 공지를 다시 확인한다.

### 라이브러리 기본값을 보완한 조건

로그인에서는 issuer, Destination, Recipient, 두 InResponseTo, bearer SubjectConfirmation, AudienceRestriction, 시간과 SessionIndex를 명시적으로 검사한다. DTD·entity 선언·comment/CDATA·복수 assertion·중복 ID·다른 서명 대상·약한 알고리즘을 거부한다. 신원은 `getAssertionXml()`의 검증된 assertion에서만 읽는다. XML 원문과 library error를 외부 응답에 넣지 않는다.

Node-SAML 5.1.0의 Redirect SLO 검증에는 Signature가 없을 때 성공 경로가 있고 metadata 생성기는 SLO POST binding을 고정한다. Wrapper는 Signature·RSA-SHA256·중복 없는 정확한 query parameter를 먼저 요구하고 bounded inflate 이후 library 검증을 호출한다. SP metadata는 구현한 Redirect SLO binding으로 생성한 후 xml-crypto로 서명한다. 이미 서명한 문서를 고쳐서 내보내지 않는다. Metadata의 실제 서명·ACS POST·SLO Redirect는 fixture에서 검증했다. 근거는 [Node-SAML source](https://github.com/node-saml/node-saml/tree/v5.1.0/src)와 설치한 동일 version의 코드다.

Library cache의 get/remove는 원자적인 replay 차단이 아니다. PoC는 browser nonce에 결합된 한 request만 보이는 읽기 view를 library에 주고 모든 검증 후 transaction·Response ID·Assertion ID를 함께 소비한다. 이번 ledger는 단일 process의 `Map/Set`이므로 replica 간 race·crash·재시작 보장은 P03-C02에서 DB로 검증한다.

### 검증 결과

- [Node 22 계약 fixture](evidence/P03-C01-contract-node22.json): 44개 통과. 정상 서명, issuer/audience/recipient/destination·시간·NameID 변조, wrapping·중복 ID·복수 assertion·XXE·크기, 서명 키 overlap/철회, 같은 process의 replay 경쟁, SLO signature/parameter/압축 제한을 검사했다.

- 같은 임시 사용자의 이메일·표시 이름을 Admin API로 바꾼 뒤 persistent NameID와 Keycloak user ID가 유지됐다. 새 RSA signing key를 활성화하고 승인한 metadata의 두 certificate로 로그인했으며 이전 certificate만 신뢰한 검증은 새 키의 응답을 거부했다.

## C02: SAML transaction과 명시적 신원 연결

`0032_saml_identity_state.sql`은 기존 사용자·subject·credential·권한·개인 memory owner를 수정하지 않고 다음 저장 구조를 추가한다.

- `user_identities`: 기존 app user와 persistent NameID·qualifier·issuer·SP 및 Keycloak user ID의 명시적 연결. Provisioning 상태·검증 시각·security epoch·최대 5분 freshness를 저장한다.
- `saml_transactions`: 최대 5분 AuthnRequest/LogoutRequest, provider 설정 hash, RelayState·browser nonce hash, 내부 return path와 일회성 소비 시각. Logout 필드는 한 묶음으로 존재해야 한다.
- `saml_message_consumptions`: configuration과 message ID hash의 unique ledger. Response·Assertion·Logout message는 같은 ID namespace를 사용하며 보존 시간은 10분이다.
- `user_sessions`의 nullable SAML binding: identity·user의 composite FK, SessionIndex·security epoch·SessionNotOnOrAfter. 기존 session의 새 필드는 모두 null이며 SAML session은 최대 8시간과 assertion session 만료 중 이른 시각을 따른다.
- `identity_admin_operations`·`identity_admin_outbox`: 명시적인 관리 작업·중복 방지·claim/retry/delivery 상태. Password·token·임의 JSON payload column은 없다. 실제 Admin API processor는 C04/C05에서 구현한다.

`apps/runtime/src/auth/saml-state.ts`의 신원 연결 API는 활성 administrator와 대상의 기존 OIDC subject를 확인한다. 연결은 pending·disabled로 생성하며 로그인이나 이메일 일치로 사용자를 만들거나 연결하지 않는다. 같은 Keycloak account를 다른 app user에 붙이거나 기존 사용자의 identity를 덮어쓰는 요청은 거부한다. 이 구현에서는 issuer 내 Keycloak account당 하나의 app user mapping을 허용한다. 여러 SP 간 공유 정책이 필요하면 별도의 명시적 변경이 필요하다.

로그인 시작 시 새 request ID·RelayState·browser nonce를 생성하고 DB에는 nonce/state hash만 보관한다. `loadSamlLogin`은 provider·browser에 결합된 미소비 transaction만 protocol verifier에 보여준다. `consumeSamlLogin`의 입력은 이미 서명·protocol 검증을 마친 신원이며 XML을 파싱하거나 서명을 대신 검증하지 않는다. C03에서 C01 verifier와 연결해야 한다.

소비 시 transaction, user, identity 순서로 잠그고 활성 사용자·검증된 identity·freshness를 검사한다. Response/Assertion hash 삽입, session hash와 binding 저장, transaction 소비를 한 DB transaction에서 commit한다. Unique 충돌이나 storage 오류가 나면 전부 rollback한다. 관리자의 사용자 차단과 같은 user lock을 사용하며 lock 대기·저장 도중 deadline이 지났는지도 마지막에 다시 확인한다. DB error detail과 token 원문은 오류에 첨부하지 않는다. Session을 만들 때 freshness를 연장하지 않는다.

`pruneSamlState`는 만료된 transaction과 message hash만 batch별로 정리하고 다른 transaction이 잠근 행은 건너뛴다. C01의 assertion 최대 age 5분·skew 1분보다 긴 message 보존 시간을 전제로 한다. 실제 route와 정리 작업 등록은 C03 이후 단계다.

### 검증

Node 22.23.2에서 새 33개를 포함한 **전체 767개 테스트가 실패·skip 없이 통과**했다. 공통 package·runtime·web build, runtime typecheck, 새 TypeScript 파일 ESLint도 통과했다. [전체 source 검증](evidence/P03-C02-source.json)과 [두 process 실행 증거](evidence/P03-C02-replicas-node22.json)에 결과와 source hash를 기록했다.

임시 PostgreSQL 17.11에 migration 31개와 기존 사용자·로컬 credential·session·repository grant·tenant membership·개인 memory fixture를 먼저 만든 뒤 0032를 적용했다. 기존 row와 ID·subject·role·group·owner가 그대로이며 pending identity를 연결해도 바뀌지 않았다.

별도 Node process 두 개와 서로 다른 PostgreSQL backend PID로 같은 응답을 동시에 소비했다. 하나만 성공했고 새 session 1개·소비 transaction 1개·message hash 2개가 남았다. 서로 다른 사용자·AuthnRequest가 같은 Response ID를 동시에 쓰는 경우도 하나만 성공했다. 새 DB pool에서 이전 응답을 재전송하면 거부한다.

Nonce·RelayState·request ID·provider·login/logout 종류 불일치, request/session 만료, 비활성·삭제 사용자와 pending·비활성·stale·미래 검증 identity를 거부했다. 별도 탭의 유효한 요청은 독립적으로 성공한다. Message ID의 다른 종류 재사용, 잘못된 session owner FK, 5분을 넘는 freshness와 불완전한 logout binding도 거부했다. DB trigger로 저장 오류와 freshness 만료를 재현해 session·소비 기록이 함께 rollback되는 것을 확인했다. 실제 user row lock 대기를 관찰한 관리자 차단 경합에서도 대기 중인 로그인이 거부됐다.

이 검증의 신원 입력은 합성된 verifier 출력이다. 실제 Keycloak 서명·HTTPS browser callback 증거는 C01과 구분하며, 앱의 실제 SAML callback·Safari/Chrome·CSRF·로그아웃·운영 provisioning/revocation은 C03–C08에 남아 있다. 현재 운영 인증은 local이며 배포 전후 DB 보존 검증은 C02 release 기록으로 추가한다.
