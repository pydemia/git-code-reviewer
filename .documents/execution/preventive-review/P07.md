# P07 실행 기록

## 공통 실행 소유권과 저장된 결과 재사용

CLI의 수동 리뷰를 암호화한 실행 기록에 연결했다. 같은 profile·repository·worktree 안에서 source/base/context/knowledge/review profile/executor/model/tool 설정이 같으면 사유를 합치고 한 프로세스에만 실행권을 준다. 중앙 동기화의 `lastSynchronizedAt`은 내용 변경이 아니므로 중복 판단에서 제외한다. 실행 모드·fallback 사유·중앙 audience·connection은 유지한다.

- `queued → claimed → running → finished`를 CAS로 기록한다. 기본 lease는 30초, 실행 중 갱신은 10초다.
- 실행 전 `claimed` 상태에서 종료된 프로세스는 lease 만료 후 교체할 수 있다. `running` 상태의 lease가 만료되면 `interrupted`로 남긴다. 프로세스 종료만으로 모델 작업의 종료를 단정하거나 재호출하지 않는다.
- 대기하는 호출자를 취소해도 실행 소유자의 작업은 취소하지 않는다.
- 저장된 결과를 재사용할 때도 현재 중앙 접근 권한과 snapshot 상태를 확인한다. 다른 identity의 결과는 저장 전에 거부한다.
- 이력 저장이나 완료 기록에 실패해도 이미 받은 보고서는 호출자에게 돌려준다. durable completion을 확인한 것으로 표시하지 않는다.
- `gcr requests`로 이 profile/worktree의 기록을 조회한다. `gcr review --retry-finished`는 저장된 terminal 결과를 명시적으로 다시 실행한다. 동시에 들어온 같은 재실행 요청은 한 세대로 합친다.

저장소는 기본 local data directory 아래 `review-requests`에 둔다. Profile별 OS credential과 암호화/CAS 파일 저장 방식을 재사용한다. Trigger별 최소 간격과 시간당 리뷰 시작 예약을 기록하는 core API도 추가했다. 예약은 모델 API 호출 횟수나 실제 token 사용량이 아니다. 현재 범위는 한 profile/worktree이며 사용자 전체 예산은 아직 없다.

## 남은 구현

P07 전체 완료가 아니다. Durable 기록은 고정된 source를 준비한 살아 있는 호출자 사이에서 실행권을 조정한다. 준비된 source payload를 보관해 headless 서비스가 독립 실행·복구하는 기능은 아직 없다. `interrupted` 요청의 결과 대조·명시적 복구 UI, 이력 retention 후 결과가 사라진 요청의 처리, 실행 기록 보존 정책도 남아 있다.

Save·Stage 이벤트 연결, 네 toggle과 repo override, debounce·우선순위·latest generation·전체 사용자 예산, headless IPC/service, 정확한 commit/push 범위, 비파괴 hook 연동과 실제 trigger별 모델 검증을 계속 구현해야 한다. 기존 Stage watcher는 아직 이 공통 실행 서비스로 교체하지 않았다.

## Save·Stage 공통 scheduler와 source 관측

## Commit index와 Push ref의 고정 source 처리

`commit-tree` source 계약과 snapshot capture를 추가했다. Source/base는 전체 commit OID를 명시하며 현재 HEAD·index로 대체하지 않는다. Force update도 전달된 두 tree를 직접 비교한다. Target branch는 명시한 ref에서만 얻고, base/source tree의 `.gitignore`와 현재 checkout의 제외 규칙을 적용한다. 현재 index가 손상돼도 commit tree 읽기는 index를 사용하지 않는다.

`resolvePrePush`는 stdin 전체를 먼저 검증하고 ref별 ready/ref-deleted/unchanged/unsupported 상태를 보존한다. 64개 ref·256 KiB 한도를 적용하며 새 ref의 base는 명시적으로 empty tree다. 삭제 ref는 source 리뷰 없이 ref-deleted로 기록한다. Commit tag는 peel하고 missing/noncommit object는 fetch하지 않고 unsupported로 남긴다.

CLI의 `review --trigger commit`은 실제 `GIT_INDEX_FILE` 또는 명시적 `--index-file`을 사용한다. `push-review`는 pre-push stdin의 모든 ref를 순서대로 리뷰하며 일부 실패·unsupported도 출력에 남긴다. 이 단계는 foreground CLI이며 독립 서비스의 비동기 advisory 접수·managed hook 설치는 아직 미완료다. Amend는 변경 전 HEAD 대비 이번 amend의 변경을 리뷰한다. 전체 parent-to-rewritten-commit diff를 추정하지 않는다.

실제 임시 Git hook으로 initial commit, `commit --only`, `--amend --only`의 capture tree가 최종 commit tree와 같음을 확인했고 관련 없는 staged 변경이 보존됐다. Local bare remote로 여러 ref, 신규 branch, force update, 삭제 ref 입력을 확인했다. SHA-256, tag peel, missing object, 저장소 변경·index 손상·tree ignore, CLI 사유 병합과 여러 ref 처리도 회귀 검사에 포함했다.

공통 client/CLI 검사 24개 파일에서 371 passed, 1 skipped다. Skip은 명시적인 실제 계정 검사다. Client alpha.20 / CLI alpha.14 패키지의 실제 계정·확장 호환 검증은 다음 기록에 추가한다.

## 독립 서비스와 암호화 source queue

공통 core에 고정 source payload의 직렬화·복원, profile별 암호화 서비스 등록·receipt 저장소, 사용자 전용 Unix socket을 추가했다. CLI의 `service start/run/status/stop`, `allow/revoke/registrations`, `job/cancel`, `enqueue`, `enqueue-push`가 이 서비스를 사용한다. Start는 설치된 CLI로 별도 프로세스를 시작하고 살아 있는 같은 profile/data directory 서비스가 있으면 기존 PID를 반환한다.

저장소/worktree의 trigger와 모델·전송 범위·리뷰별 예산은 사용자가 `service allow`로 명시한다. 신규 서비스는 모두 비허용이며 repository 파일과 enqueue 인수가 실행 권한을 추가하지 않는다. 등록 교체·폐기는 실행 중 요청을 취소하고 이전 revision의 대기 요청을 폐기한다. 접수는 고정 payload가 암호화되어 저장된 뒤 반환하며 모델 완료는 receipt의 terminal 상태와 별도 보고서로 확인한다.

Snapshot 복원은 파일 바이트·line count·content/Git blob hash·제외 정책·원래 snapshot hash를 검사한다. 원본 저장소 삭제 후에도 복원 가능한 것을 source 검사에서 확인했다. 실제 CLI 실행은 현재 worktree identity와 지식을 다시 확인하므로 저장소 삭제 후 모델 실행까지 보장하는 것은 아니다. Payload 최대 8 MiB, queued/running/interrupted 합계 최대 64개다.

서비스 owner는 암호화 CAS 기록과 OS process 생존 상태로 판별한다. 실제 별도 Node 프로세스를 SIGKILL한 뒤 대기 요청은 저장한 원본 바이트로 재개하고 이미 시작했던 요청은 interrupted로 남겨 재실행하지 않았다. 중복 live owner가 기존 socket을 끊지 않는 것, socket 위치의 일반 파일 보존, 등록 폐기 후 취소, 종료 중 저장소 오류와 미완성 IPC 입력의 정리도 검사했다. IPC socket 0600·상위 디렉터리 0700은 확인했지만 다른 UID의 실제 접속 시도는 아직 검증하지 않았다.

공통 라이브러리·CLI 회귀 검사 26개 파일에서 381 passed, 1 skipped다. Skip은 명시적으로 실행하는 실제 계정 검사다. 독립 서비스 core 검사 6개와 CLI 검사 2개가 포함된다. Client alpha.21과 CLI alpha.15를 새 버전으로 패키징했고 깨끗한 consumer에서 버전·import·CLI 진입점 검사를 통과했다. 패키징 첫 검사에서 발견한 export 버전 불일치는 수정한 뒤 다시 검증했다.

Headless 파일 감시·OS 로그인 자동 시작, 사용자 전체 호출/token 예산, interrupted 결과 대조·receipt 보존 정책, Commit Defender의 Commit·Push toggle과 managed hook 설치, 16개 toggle 조합 검증은 계속 남아 있다. 이번 서비스 artifact는 기존 설치된 확장의 이벤트 경로를 자동으로 변경하지 않는다. 실제 패키지의 비동기 commit/push 검증은 후속 증거에 기록한다.

## 설치한 서비스의 실제 비동기 Commit·Push 검증

CLI alpha.15/client alpha.21 설치본을 독립 서비스로 시작하고 임시 저장소에만 advisory hook을 두었다. 실제 `git commit --only`와 local bare remote로의 `git push`가 반환된 뒤 각각의 receipt가 running인 것을 확인했다. 두 호출 모두 Git 작업이 끝난 후 서비스가 실제 `gpt-6-astra / xhigh` 리뷰를 완료했고 finding 1개씩을 기록했다.

Commit 보고서의 source tree는 실제 최종 commit tree와 같고 관련 없는 staged 변경은 유지됐다. Push는 pre-push stdin의 이전·새 commit을 사용했으며 실제 remote ref 갱신도 확인했다. 두 모델 리뷰는 각각 source-read 7건으로 source/base·caller·테스트 파일·package.json을 읽었다. 모델이 테스트 명령을 실행한 것은 아니다. 공통 실행 기록 두 개 모두 generation 1·finished였고 서비스 중복 start는 기존 PID를 반환했다.

검증 서비스의 프로세스 종료를 확인한 뒤 테스트 profile의 기본·review-requests·local-service OS key와 암호화 기록, 임시 저장소를 정리했다. 실제 다른 UID 검사는 비대화식 sudo에 비밀번호가 필요해 수행하지 못했으며 기존 mode 검사로 대체 완료 처리하지 않았다. 상세 근거와 artifact hash는 `evidence/P07-service.json`에 기록했다. 구현 commit은 `29d1794`이며 원격 branch에 push했다. CLI는 독립 consumer에 설치했으며 Commit Defender의 기존 설치본과 PRISM 서버는 이번 변경의 배포 대상이 아니다.

## Hook 연동을 위한 서비스 실행 예산

Commit Defender의 시간당 자동 리뷰 설정을 서비스 등록에 전달하도록 `maximumReviewsPerHour`와 `service allow --reviews-per-hour`를 추가했다. 기본 6, 범위 1–100이며 기존 공통 profile/worktree 실행 기록을 사용한다. 시작 한도에 도달하면 모델을 호출하지 않고 고정 payload를 queued/notBefore로 유지한다. 이미 저장된 같은 입력의 결과를 재사용할 때는 새 시작을 차감하지 않는다. 사용자 전체 예산은 별도 잔여 범위다.

확장은 서비스 status의 `review-start-budget-v1` 기능 표시를 확인해야 한다. 이 기능이 없는 이전 서비스에 자동 hook 권한을 새로 등록하지 않는다. 관련 CLI·독립 서비스·공통 실행 기록 검사 19개와 client/CLI build, 새 client alpha.22/CLI alpha.16 패키지의 독립 설치 검사가 통과했다. 실제 확장 hook의 전달 검증은 Commit Defender 연동 기록에 추가한다.

## 중단 요청과 서비스 receipt의 완료 결과 복구

Client alpha.27 / CLI alpha.23에 `requests reconcile --key HASH --generation N`과 `service reconcile --id ID`를 추가했다. 실행기는 terminal 보고서를 받은 뒤 이력 저장 전에 보고서 ID/hash/generation을 별도 암호화 receipt에 기록한다. 복구는 그 receipt와 저장된 보고서의 전체 hash·execution identity·현재 중앙 인가를 대조한다. 살아 있는 lease나 완료 근거가 없는 요청은 복구하지 않는다. 같은 source라도 이전 generation의 보고서는 연결하지 않는다.

서비스 receipt는 모델 실행 전에 공통 요청의 key/generation에 연결된다. 등록 revision·trigger·worktree·profile·실행 mode/connection도 대조한다. 이력이나 공통 완료 기록을 저장하지 못하면 `completionUnconfirmed: true`와 interrupted 상태를 남겨 source payload를 보존한다. 확인한 결과를 복구하면 원래 run ID·상태를 기록하고 payload를 삭제한다. 중단 확인은 owner token을 제거해 이전 소유자의 heartbeat/finish를 막으며 새 실행 시도가 없으므로 generation을 늘리지 않는다. 기존 요청 schema는 유지하고 새 receipt는 별도 저장한다.

고유 회귀 검사 69개와 타입 검사·변경 파일 lint를 통과했다. 실제 HTTPS fixture의 중앙 결과 복구와 철회 후 거부, 변조된 보고서·이력 부재·다른 generation·살아 있는 lease·완료 receipt 저장 실패를 포함한다. 별도 Node 서비스 프로세스를 이력 저장 직후 `SIGKILL`하고 재시작해 원래 완료 보고서를 복구했다. 작업 파일을 수정한 뒤에도 원래 source hash가 유지됐고 합성 executor 호출은 한 번이었다. 모델 호출을 수행하는 opt-in 검사 1개는 이번 회귀 실행에서 제외했다.

새 client tarball 세 개와 CLI alpha.23의 독립 Node 22 설치를 검증했다. CLI SHA-256은 `7dfc8a4461ec1cc0280b7f4ac726c2abd821b54ca6b1ebef8049d121741795bd`다. 설치본에서 실제 서비스를 시작해 `review-reconciliation-v1`, 같은 PID의 중복 start, 미등록·빈 작업 상태, 잘못된 receipt와 없는 completion의 거부를 확인했다. 모델·자동 등록 없이 서비스를 종료하고 소유 PID 종료, OS key 2개와 임시 파일 정리를 확인했다.

[운영 절차](../../../docs/operations/local-review-recovery.md)와 [검증 증거](evidence/P07-recovery.json)에 범위를 기록한다. Commit Defender의 복구 UI와 새 service artifact 연결·설치는 후속 전달이다. 이전 client에서 완료 receipt 없이 중단됐거나 generation이 별도로 fence된 기록은 추정 복구하지 않는다. 사용자 전체 예산·headless 감시·누락 이벤트·trigger 조합·보존 정책 및 P07 전체 완료 조건은 남아 있다. 사용자 global CLI·VS Code 설치본·PRISM runtime은 이번 CLI/core 변경에서 바꾸지 않았다.

## 네 trigger의 16개 실행 조합

Commit Defender `eee866c`에서 설정값 검사에 더해 Save·Stage 이벤트, 실제 managed hook, 전달된 CLI alpha.23의 source capture와 IPC, client alpha.27의 공통 broker를 연결한 16개 조합 검사를 추가했다. Editor scheduler에 테스트 전용 시계를 주입하며 제품의 기본 시계와 자동 실행 설정은 유지한다. 재현 명령은 CD `vscode-extension`에서 Node.js 22 이상으로 실행하는 `npm run test:trigger-matrix`다.

최종 16개 조합과 기존 자동 리뷰 회귀 15개, source/test 타입 검사와 build가 통과했다. 모든 조합을 합쳐 합성 executor 28회, Commit/Push hook 접수 48개가 발생했다. 각 조합의 durable 요청 사유는 켜진 trigger와 일치했고 같은 입력의 반복 hook은 저장된 결과를 재사용했다. 네 trigger를 모두 켠 경우 Save의 working-tree 1회, Stage·Commit 공통 index 1회, Push의 commit-tree 1회다. Hook 접수마다 공통 요청 key와 결과 run ID의 일치, finished/completed를 확인했으며 실제 push 후 bare remote의 HEAD도 일치했다.

VS Code 이벤트 발신부와 executor는 합성이며 실제 모델 호출은 0회다. 서비스 실행 callback은 전달된 core API를 조합하므로 CLI service-run 인자 해석이나 실제 모델의 동시 trigger 경로 전체를 이 검사로 통과 처리하지 않는다. 서비스 lease와 Git은 실제 시간을 사용하고 editor scheduler만 제어 시계를 사용한다. 최종 검사에서는 OS credential을 사용하지 않았으며 소유 서비스 종료와 응답 불가, 고유 profile·hook 디렉터리·Git fixture·메모리 key 정리를 확인했다. 공용 불변 runtime cache는 유지한다.

[실행 증거](evidence/P07-trigger-matrix.json)에 조합별 호출·요청 사유와 로그 hash를 기록했다. 이번 변경은 검증기와 선택적 시계 port이므로 새 VSIX 설치나 서버 재배포를 수행하지 않았다. 실제 모델의 중복 trigger 경로, closed-host Save/headless 감시, partial-hunk unstage, 사용자 전체 예산·보존·다른 UID 및 P03–P06·P09–P13의 잔여 조건은 유지한다.

## Stage·Commit의 실제 중복 실행 수정과 2.7.1 전달

실제 VS Code에서 Stage 리뷰 실행 중 pre-commit hook을 요청하자 서로 다른 source hash로 모델 두 개가 시작되는 결함을 확인했다. Stage는 선택 파일을 먼저 읽고 Commit은 경로 순서로 읽는데, 같은 파일 집합을 담은 배열의 수집 순서까지 hash에 포함된 것이 원인이었다. 앞선 단일 변경 파일 중심 16개 조합 검사는 이 차이를 드러내지 못했다. 변경 파일보다 먼저 정렬되는 호출부를 추가하자 기존 alpha.27의 Stage·Commit 조합에서 합성 호출 2회로 재현됐다.

GCR `d4e67fb`는 capture를 마친 파일 map을 정렬한 뒤 hash와 직렬화에 사용한다. 선택 파일의 수집 우선순위와 byte/file budget은 유지하고 다른 선택 범위는 합치지 않는다. Client alpha.28과 CLI alpha.24를 새 immutable artifact로 만들었고 CD `6ff8d06`의 2.7.1에 전달했다. 기존 alpha.27 snapshot 두 개는 Node 18.20.8/22.23.2의 새 core에서 기존 identity·순서 그대로 복원됐다. 기존 요청 기록을 새 hash로 다시 쓰거나 버전 간 중복 제거를 검증한 것은 아니다.

GCR source/CLI 서비스 회귀 33개와 context/request 회귀 34개, CD 전체 195개와 강화한 실행 조합 16개·계수기 1개가 통과했다. Source/test 타입 검사와 build·변경 파일 lint, 새 artifact의 독립 소비도 확인했다. 신규 source 검사에는 Git capture 세 번에 맞춰 20초 제한을 적용했다. 초기 패키지 version metadata·vendor provenance 누락과 build 중 import 실패는 최종 산출물 확정 전에 수정하고 해당 검사를 다시 통과했다.

최종 VSIX의 VS Code 1.135.0에서 Stage 모델 실행 중 Commit 사유가 같은 running 요청에 합류했다. 실제 현재 계정 Astra/xhigh 실행은 1회였고 75,155 ms 뒤 completed·결함 1개를 저장했다. Source/base의 sum.ts·caller.ts·sum.test.ts·package.json을 8회 읽었으며 테스트 명령은 실행하지 않았다. 이후 실제 Git commit의 두 번째 hook 접수도 같은 key·generation 1·run ID `a7e862c7-b453-4432-b3b8-27faeeb87691`를 재사용했다. Stage 대기 해제, 소유 프로세스 89개 종료·OS key 3개·fixture 정리를 확인했다. 같은 VSIX의 최소 VS Code 1.90.2 활성화·26개 command도 통과했다.

첫 native 시도는 socket 경로 길이 제한으로 모델 호출 없이 종료됐다. 두 번째 시도는 로컬 도구 검사 두 번까지 세는 계수기 오류로 실제 리뷰 한 번이 취소됐다. 계수기를 합성 검사로 수정한 다음 실제 제품의 hash 결함을 발견했으며, 이때 남아 있던 Commit 리뷰는 완료를 관찰한 후 서비스를 종료했다. 각 시도의 원본 증거와 최종 성공 범위를 분리했고 모든 소유 자원을 정리했다.

소스 push 후 기존 2.7.0을 백업하고 검증한 VSIX로 2.7.1을 설치했다. 실행 파일 7개가 검증본과 동일하며 package manifest는 VS Code가 추가한 `__metadata`를 제외한 모든 필드가 일치한다. 사용자 창을 강제로 reload하거나 global CLI를 교체하지 않았다. 서버 runtime·Helm·DB TLS 변경은 없다. [전달 증거](evidence/P07-source-order.json)에 artifact hash, 실패·수정·실제 합류·설치 범위를 기록했다. P07의 closed-host Save/headless 감시·partial-hunk unstage·사용자 전체 예산·보존·다른 UID와 이전 phase 잔여 조건 및 P09–P13은 유지한다.


## CLI의 독립 Stage·외부 Save 감시

GCR `7cad26d`에서 `watch start/status/stop`을 독립 서비스에 연결했다. Stage는 실제 index를, Save는 외부 파일 쓰기를 재조회한다. Save는 `--external-changes` 허용이 필요하다. 처음 시작할 때 기존 변경을 기준점으로 삼고 관측값·debounce 대기·제출 intent를 암호화해 저장한다. 서비스가 중단돼도 같은 intent를 같은 receipt로 확인하며 실행 결과가 불확실한 요청은 자동 재호출하지 않는다. 감시 해제와 최신 입력의 취소 의도를 먼저 저장하고 큐가 실행 직전 다시 확인한다. 일반 enqueue·hook의 권한과 요청은 보존한다.

Client alpha.29·CLI alpha.25를 immutable artifact로 만들고 독립 consumer에 오프라인 설치했다. Node 18.20.8/22.23.2의 공통 패키지 import, Node 22.23.2의 CLI 설치·27개 회귀 검사, source/test 타입 검사와 변경 파일 lint가 통과했다. 실제 서비스 프로세스를 SIGKILL한 뒤 재시작하는 검사에서 Stage 대기 복원과 실행 한 번을 확인했다. 처음 실패한 두 검사는 반환값 비교와 테스트용 키 버퍼 복사 문제를 수정한 뒤 통과했다.

설치한 CLI의 `watch start` 명령이 종료된 뒤 임시 저장소의 sum.ts를 수정했다. VS Code 없이 서비스가 현재 계정 Astra/xhigh 리뷰를 실행해 73,792 ms에 completed·결함 1개를 저장했다. 실제 run ID는 `d987dc62-c073-4e90-89ef-72bc62e42129`이며 공통 요청은 generation 1 한 건이다. Source/base 읽기 8회를 확인했으며 테스트 명령은 실행하지 않았다. 동일 바이트의 재저장에는 새 receipt가 생기지 않았다. 소유 서비스 종료·전용 OS key 3개·fixture 정리를 확인했다. [전달 증거](evidence/P07-headless-watch.json)에 패키지 hash와 검증 범위를 기록했다.

이 전달은 CLI 감시 기능이다. 현재 설치된 CD 2.7.1의 Save/Auto Save 설정과 연결하는 작업은 남아 있으며 CLI가 editor 쓰기의 출처를 구분한다고 주장하지 않는다. 기존 사용자 설정에서 감시를 켜거나 global CLI·VSIX·서버·Helm·DB TLS를 교체하지 않았다. CD 이벤트 출처 전달과 headless 전환, partial-hunk unstage, 사용자 전체 예산·보존·다른 UID, 이전 phase와 P09–P13 잔여 조건을 계속 진행한다.


## Editor Save 출처 전달과 2.8.0 설치

GCR `479240a`와 Commit Defender `3e80673`에서 Save·Stage를 Commit·Push와 같은 독립 서비스로 연결했다. Editor가 붙어 있는 동안 파일 hash와 manual/Auto Save/external 출처를 IPC로 전달한다. 제외한 Auto Save의 바이트가 반복 filesystem 이벤트로 허용되는 것을 막고 typing은 해당 파일의 대기를 취소한다. 마지막 editor가 정상 종료하면 허용된 외부 변경 감시를 이어가며 이미 접수한 리뷰는 계속 실행한다. 비정상 종료 직전 출처를 전달하지 못한 변경은 미분류 경로로 표시해 수동 리뷰를 안내한다.

완료된 Save·Stage 결과는 현재 workspace/profile/connection과 source를 확인한 뒤 Problems·inline comment·이력에 반영한다. 이후 파일 수정으로 이전 진단을 제거하며 더 최근의 수동 리뷰 표시를 덮어쓰지 않는다. 중앙 연결을 선택한 서비스는 등록된 commit-defender client binding을 사용한다. 일반 CLI의 gcr-cli binding 조건은 유지하며 이 연결 분기는 합성 HTTPS 서버로 검증했다.

Client alpha.30·CLI alpha.26을 immutable artifact로 만들었다. GCR 회귀 47개 통과·실제 계정 opt-in 1개 제외, transition 검사 13개 재확인, Node 18/22 import와 독립 CLI 설치를 확인했다. CD 전체 회귀 197개, source/test 타입 검사, 자동 실행 16개 조합이 통과했다. 조합 전체의 합성 executor 호출은 28회이고 서비스 receipt는 64개다. 모든 trigger를 켰을 때 Save 1회, Stage·Commit 공유 1회, Push 1회이며 foreground 자동 실행은 없었다. 이 조합 검사는 서비스 debounce의 정확한 시간 경계를 검증하지 않는다.

최종 VSIX를 VS Code 1.135.0에서 실행해 제외한 Auto Save의 접수·모델 호출 0회, 허용한 Save 완료 후 Problems 진단 1개와 수정 시 제거를 확인했다. 두 번째 Save가 running일 때 창을 닫아 정상 detach와 실행 지속을 확인했고, 종료 후 새 외부 변경도 리뷰를 완료했다. 실제 현재 계정 Astra/xhigh 실행은 총 3회이며 각각 70,433 ms·63,796 ms·72,453 ms, completed·결함 1개를 기록했다. 고정 source/base 읽기는 각각 8·7·7건이며 모델은 테스트 명령을 실행하지 않았다. 소유 프로세스 210개 추적 결과 잔여 0개, OS key 3개와 fixture 정리를 확인했다.

같은 VSIX는 최소 VS Code 1.90.2에서 활성화·26개 command·빈 이력의 key 미생성 검사를 통과했다. 양쪽 소스를 push하고 기존 2.7.1을 백업한 뒤 2.8.0을 사용자 VS Code에 설치했다. 실행 파일/manifest 7개는 검증 artifact와 byte 단위로 같고 package.json은 VS Code의 __metadata를 제외한 모든 필드가 같다. VSIX SHA-256은 `d5e394c7aef40a972741c210fd37540311819c15d3395753513f58517fb6c035`다. 열린 창 reload와 global CLI 교체는 없으며 서버·Helm·DB TLS 설정은 유지했다.

[전달 증거](evidence/P07-editor-save.json)에 source/artifact hash, 실제 보고서 ID, 조합별 실행과 설치 근거를 기록했다. Editor 활성화 전 쓰기와 실패한 인계·비정상 종료 전체, 수동/서비스 실행 우선순위, partial-hunk unstage, 사용자 전체 예산·보존·OS login autostart·Linux/다른 UID 검증은 남아 있다. 정상 종료 검증으로 이 조건들을 완료 처리하지 않는다. P07 전체와 P03–P06 잔여 운영 조건, P09 공개 출시 및 P10–P13은 계속 진행한다.
