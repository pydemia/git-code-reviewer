# P08 실행 기록

## P08-C01: 로컬 리뷰 대화와 질문 checkpoint

구현 commit: `b55c98d` (`feat: persist interactive local review conversations`).

`client-contract`에 대화·turn·질문·인용·예산 계약을 추가했다. Web `chat-run`의 질문 길이와 선택지 제한, 상태 어휘를 로컬 계약에 옮겼으며 서버 session/account ID와 DB 의존성은 포함하지 않았다. 로컬 인용은 기존 `SourceLocation`을 사용한다.

`ReviewConversationStore`는 원래 리뷰 보고서·고정 source·실행 identity·대화·질문·재개 상태를 하나의 암호화 CAS record로 저장한다. 기존 단순 chat archive와 namespace를 분리했고 profile/repository/worktree와 중앙 audience를 검사한다. 다른 중앙 사용자나 standalone 선택에서는 해당 대화를 조회·목록·삭제할 수 없다. Source와 context identity가 달라지면 기존 대화의 실행을 거부한다. 저장된 identity나 사용자 답변으로 실행 권한을 발급하지 않는다.

`runReviewConversation`은 현재 권한을 확인한 뒤 한 worker만 실행한다. Codex `converse`에만 `ask_user`를 노출하며 질문·call ID·사용 예산을 저장한 뒤 프로세스를 취소한다. 사용자 응답은 같은 turn을 queued로 바꾸고 다음 호출이 새 격리 프로세스에서 저장된 대화를 재구성한다. Provider thread, 비공개 추론, credential은 저장하지 않는다. 이전 단계의 인용 ID는 재사용할 수 없고 현재 단계에서 반환된 `read_file` 범위만 인용할 수 있다. Search 결과를 직접 소스 인용으로 취급하지 않는다.

모델 호출·전송 바이트·tool 호출·실행 시간은 응답 후에도 같은 turn의 예산에서 차감한다. 사용자 응답 대기는 실행 시간을 사용하지 않는다. 결과가 확인되지 않은 running 작업은 예약을 유지하며 명시적 `interrupt`가 failed/interrupted로 닫을 뿐 모델을 다시 호출하지 않는다. 중복 응답은 같은 답이면 같은 revision을 반환하고 다른 답은 거부한다. 취소·종료·삭제 뒤 도착한 결과나 질문은 이전 CAS revision으로 덮어쓸 수 없다.

Host가 호출하는 `prune`는 기존 chat retention 설정을 사용한다. 24시간 동안 답하지 않은 질문을 expired로 종료하며 queued/running 실행은 나이만으로 삭제하지 않는다. UI의 startup/terminal 변경에서 이 메서드를 호출하는 연결은 P08-C02에 포함한다.

## P08-C02 — Commit Defender 대화 화면과 worker

Summary의 Discuss review, history 항목, command palette에서 원래 보고서의 대화를 연다. Finding 선택은 질문 초안만 만들고 명시적 전송 뒤 모델을 호출한다. Review 요약·finding, 사용자 질문·확인 답변, 모델 답변·source evidence, 실행 상태를 구분한다. Enter 전송, Shift+Enter 줄바꿈과 IME 입력, draft 보존, 질문 저장 후 재개, 명시적 취소·queued resume를 연결했다.

대화 worker는 현재 trusted workspace·profile·connection 선택을 다시 확인한다. 원래 source·context·executor와 승인 정책을 재구성하고 다른 선택이나 변경된 지식에서는 실행하지 않는다. 같은 중앙 publication의 정상 재동기화는 관측 시각만 갱신하므로 원래 identity의 관측 시각을 유지하되 현재 authority와 context를 별도로 검증한다. UI는 provider 비공개 추론 대신 source 조회와 대기·취소 상태를 표시한다. Worker 종료와 자식 프로세스 정리 후에 결과를 전달한다.

원래 보고서와 고정 source는 암호화 conversation record로 보존한다. CD의 수동·Save·Stage 경로와 GCR CLI의 Commit·Push 서비스 경로에 같은 보존 처리를 추가했다. 고정 source가 없는 예전 보고서는 현재 작업 파일로 대체하지 않는다. UI의 source 버튼은 host가 발급한 ID와 render revision만 전달하며 worker가 검증한 인용 위치의 저장된 source를 readonly 문서로 연다. 임의 경로나 command URI를 전달하지 않는다.

GCR CLI의 보존 구현은 `2f3bb73`이며 CLI `0.1.0-alpha.17`에 포함된다. CD는 공통 패키지 `0.1.0-alpha.23`과 CLI alpha.17의 tarball·manifest hash를 고정한다. 전역 CLI는 바꾸지 않는다. 이 변경은 client 기능이며 PRISM 서버 배포나 DB TLS 구성을 변경하지 않는다.

## P08-C03 — 명시적 제출 API와 연결별 대기열

`reviews:submit`과 `feedback:submit`을 새 API key 발급 시 각각 선택한다. 기존 key와 기본 발급은 `knowledge:read`를 유지한다. 서버의 새 result/feedback endpoint는 bearer와 audience를 검사하고 쓰기 transaction에서 credential·현재 사용자·tenant/repository 인가를 재확인한다. 같은 destination/user/client/request ID와 payload는 key 재발급 후에도 같은 receipt를 반환하고 다른 payload는 충돌로 거부한다.

계약은 결과의 상태·건수, review/source/context/snapshot 참조와 사용자가 고른 feedback message·finding/rule/source 위치만 받는다. Report, chat, source body, 개인 지식 field를 거부한다. 서버의 근거는 항상 `client-reported`이며 접수만으로 기준 승인·예외 승인·모델 생성·실제 테스트 근거를 만들지 않는다. 과거 manifest가 이미 정리된 경우 참조를 검증된 snapshot이라고 표시하지 않는다. Migration 0043은 제출 테이블과 key scope의 허용 집합만 추가한다. 데이터는 30일 뒤 목록에서 제외하고 기존 retention command가 삭제한다.

`prepareReviewSubmission`은 보고서에서 공개 참조·건수만 추출한다. `ReviewSubmissionQueue`는 사용자가 확인한 payload hash가 같아야 enqueue하며 전송은 별도 명시적 호출이다. 연결별 암호화 저장, CAS 전송 lease, 응답 유실의 동일 ID 재전송, 명확한 HTTP 거부의 명시적 재시도, 취소와 30일 정리를 구현했다. 제출 오류는 knowledge cache를 변경하지 않는다. 연결 변경 후에도 만료된 로컬 payload 정리가 가능하며 startup에서도 정리한다.

관련 client/CLI/웹 회귀는 29개 파일 407 passed·기존 opt-in 1 skip이다. 보존 처리 보완 후 대기열 집중 검사 3개를 다시 통과했다. 실제 PostgreSQL/API 검증은 별도 기록을 따른다. 초기 HTTP transport fixture가 명시적인 loopback 허용을 빠뜨려 실패했고 기존 시험용 허용 옵션을 적용했다. 패키징의 dist 정리와 검사를 동시에 실행한 한 시도는 import 단계에서 멈췄으며 패키징 종료 뒤 같은 검사를 순차 실행했다. 제품의 HTTP/TLS 정책을 완화하지 않았다.

공통 library `0.1.0-alpha.24`를 새 불변 tarball로 생성하고 Node 22.23.2의 독립 consumer에서 import를 확인했다. CLI/MCP command와 CD 제출 확인 화면·승인/재동기화는 P08-C04/C05에 남아 있다. 운영 배포 완료 여부는 후속 배포 증거에 기록하며 전체 goal을 계속 유지한다. [API·대기열 계약](../../../docs/operations/review-submissions.md)을 따른다.


### C03 운영 경로 보완

Production image alpha.43의 실제 server 등록 검증에서 Origin이 없는 native bearer POST가 웹 세션 CSRF 검사에 걸려 403을 반환했다. 해당 이미지는 PRISM-DEV에 배포하지 않았다. 명시된 submission route에서 Authorization이 있고 Origin이 없는 요청만 Origin 검사 예외로 처리하고 기존 scoped bearer 인증과 트랜잭션 내 재인증을 유지했다. Origin을 보낸 요청은 같은 origin이어야 하며 cookie만 보낸 요청과 다른 API의 bearer 요청은 예외가 아니다. Production Origin guard를 사용하는 PostgreSQL 통합 검증 12건이 통과했다.

제출 응답의 권한 부족과 실제 인증 철회를 구분했다. 확인된 철회·인증 실패는 원래 연결과 credential을 폐기하고 offline cache 사용을 차단한다. Identity 조회 장애는 자격 증명을 보존하되 성공한 sync 전까지 cache 사용을 차단한다. 이전 cache generation의 응답이 새 sync나 재연결 상태를 덮어쓰지 않도록 했다. Cache·HTTP·제출 대기열 집중 검증 84건이 통과했다. 이 변경은 client alpha.25 / CLI alpha.19와 서버 alpha.44 릴리스 후보에 포함하며 실제 배포 성공은 후속 증거로 확인한다.

Migration은 42→43이며 서버·worker의 `verify-full`, 기존 데이터·Secret·HTTPRoute·PVC와 identity replica 2개를 보존했다. 배포 전 DB backup은 암호화 readback을 검증했으며 restore를 실행한 것은 아니다.

Client alpha.25와 CLI alpha.19를 Node 22.23.2에서 독립 패키지로 검증했다. 설치한 client library와 macOS Keychain을 사용해 실제 PRISM-DEV HTTPS에 연결하고 미확인 payload 거부, enqueue만으로 전송하지 않음, read-only key의 제출 거부, feedback/result 제출, 같은 ID·payload의 동일 receipt, 개인 원문 필드 거부를 확인했다. Key를 폐기한 뒤 제출과 offline review가 모두 거부됐고 연결은 disconnected로 바뀌었다. 서버 조회에 나타나는 것은 `client-reported` 제출 기록이며 승인된 기준이 아니다. 검증용 사용자·저장소·Keychain 항목·로컬 파일을 정리하고 기존 행과 리소스 보존을 다시 확인했다. 외부 모델 호출은 0회다.

[배포와 실제 제출 증거](evidence/P08-feedback-submission.json)에 패키지 hash, 이미지·chart·live 검증 결과를 기록했다. 사용자 VS Code 설치본과 global CLI는 이번 C03 작업에서 교체하지 않았다. 다음 작업은 P08-C04 CLI/MCP 연결과 P08-C05 제출 확인 화면·후보 승인·재동기화다. 전체 P00–P13 goal은 계속 진행한다.


## P08-C04 — CLI/MCP의 준비된 리뷰와 제출 경로

CLI `0.1.0-alpha.20`은 client alpha.25를 그대로 사용하며 추가 runtime dependency 없이 stdio MCP adapter를 포함한다. 소스 commit은 `8e2d5ae`다. `prepare`는 기존 snapshot adapter로 캡처한 source·base·diff를 profile/repository/worktree별로 암호화해 24시간 보관한다. `context`, `read-source`, `get-rule`, `review --prepared`는 같은 source를 사용하고 현재 context·client·중앙 연결의 일치와 권한을 다시 확인한다. 적용 지식 또는 context identity가 바뀌면 새 준비가 필요하다. 준비 성공은 모델 리뷰 완료로 표시하지 않는다.

`submit-review`와 `feedback`에 preview/queue/send/show/cancel/list를 연결했다. 미리보기는 공통 projection의 public payload와 hash를 반환하고 저장·전송하지 않는다. Queue에는 정확한 확인 hash가 필요하며 send를 별도로 호출해야 HTTPS 요청을 보낸다. 제출 권한 부족은 리뷰 cache를 유지하고 확인된 key 철회는 준비된 중앙 source 조회도 차단한다. API 응답은 계속 `client-reported`이며 maintainer 승인된 기준과 구분한다.

`gcr mcp`는 시작 시의 Git worktree·profile·data directory·mode·connection·executor를 고정한다. Tool 인수로 이 범위를 바꿀 수 없다. 기본 도구는 status/prepare/context/source/rule/result이며 중앙 연결에서 sync를 제공한다. `--allow-review`, `--allow-submissions`로 해당 도구를 명시적으로 노출한다. 초기화만으로 watcher·sync·모델·제출을 시작하지 않는다. MCP 초기화·protocol 협상·bounded NDJSON·취소·재접속·안전한 오류 응답을 구현했으며 진행 중 review와 별도로 ping/cancellation을 처리한다. Review는 terminal report를 반환하는 foreground 호출이며 비동기 접수 receipt를 가장하지 않는다.

[운영 문서](../../../docs/operations/local-mcp.md)에 설치·host 설정·CLI/MCP 계약과 지원 범위를 기록했다. 설치 패키지의 실제 host·모델 검증 결과는 후속 증거에 기록한다. CLI/MCP 대화 turn 연결, P08-C05의 CD 제출 확인·승인·재동기화, P08-C06 Skill과 나머지 P00–P13 완료 조건은 남아 있다. 사용자 global CLI·VS Code 설치본·MCP 설정과 PRISM-DEV 서버를 이번 CLI 작업에서 변경하지 않았다.


### C04 설치 패키지와 host 검증

CLI/central/MCP/service 회귀 4개 파일에서 36건이 통과하고 별도 opt-in 실제 모델 테스트 1건을 건너뛰었다. Typecheck·lint와 Node 22.23.2의 독립 tarball 설치 검증을 통과했다. Alpha.20에서 실제 MCP Inspector 2.6.0 연결과 공식 SDK 1.30.0의 준비→재접속→같은 source/context/rule 조회, 범위 밖 source 거부를 확인했다.

별도 `gcr_review_changes` 실제 Astra/xhigh 호출은 tool error로 종료돼 성공 검증을 완료하지 못했다. 처음 검증 도구가 보고서 앞 600자만 실패 메시지에 남겨 terminal status/problem을 보존하지 못했다. 실행 시작부터 fixture 정리까지 약 10분이 걸렸지만 정확한 실패 원인을 timeout으로 단정하지 않는다. 후속 검증 도구는 assertion 전에 반환 보고서 전체를 보관하도록 보완했다. 이 executor 호출을 재실행하지 않았으며 성공한 리뷰로 집계하지 않는다.

다른 검증용 worktree에서 실제 Codex CLI 0.154.0 호스트를 현재 계정의 Astra/xhigh로 실행했다. MCP의 status/prepare/source/context/rule을 호출하고 준비된 source hash를 최종 답변에 인용했다. `total.ts`에서 정수 센트 합계를 `/ 100`으로 나누는 계약 위반과 `[150, 75]`가 `225` 대신 `2.25`가 되는 사례를 소스로 판단했다. 셸·파일 수정·별도 executor 리뷰·제출은 호출하지 않았다. Host 자체 모델의 소스 판단과 `gcr_review_changes` 실행 검증은 구분한다.

Codex host는 requireSource 형식과 builtin을 requireKnowledge에 지정하는 잘못된 요청을 두 번 보낸 뒤 기본 prepare로 복구했다. 도구 schema에 `source:relative/path`/`base:relative/path`와 local memory/user-authored skill ID의 의미를 추가했다. 이 수정은 `911ec67`의 CLI alpha.21이며 최종 tarball SHA-256은 `a4e40a1e1b0067a317f49e98090b50cf7b1428754204117d6a0753068c7c85f8`이다. Alpha.21 설치본에서 Inspector·SDK 연결, 재접속·고정 source/context/rule, 명시적 source 참조와 보완된 인수 설명을 추가 모델 호출 없이 확인했다. 실제 Codex 모델 host 검증은 alpha.20에 대한 증거이며 alpha.21에서 다시 모델을 실행했다고 표시하지 않는다.

두 실제 모델 호출을 포함한 검증용 profile의 Keychain 항목과 로컬 파일을 정리했다. [C04 검증 기록](evidence/P08-MCP.json)은 완료한 경로와 실제 executor 검증 미완료를 함께 보존한다. P08-C04 전체 완료나 전체 goal 완료로 판정하지 않는다.


## P08-C05 — Commit Defender 제출 확인·대기열·로컬 후보

Commit Defender `2.4.0`의 source commit은 `221afd6`이며 공통 library alpha.25를 사용한다. 리뷰 요약·이력·명령 팔레트에서 제출 화면을 연다. 현재 worktree/profile의 저장된 보고서를 확인한 뒤 오탐·예외·새 판단 또는 최소 결과 metadata를 선택한다. 서버·tenant·repository·user·공개 범위와 실제 payload를 표시하며 확인한 hash만 보류하거나 전송한다. 원문 report/chat/source/local knowledge를 자동으로 포함하지 않는다.

보류는 암호화 outbox에만 저장하며 재개·새로고침·지식 동기화가 전송을 시작하지 않는다. 같은 entry를 다시 확인해 재전송하면 request ID를 유지한다. 서버 접수와 기준/예외 승인을 구분하고 접수 여부가 불명확한 실패를 성공으로 표시하지 않는다. 별도 사용자 선택으로 feedback message를 repository Local Memory candidate에 저장하며 자동 활성화하지 않는다. Workspace trust·설정·profile·선택 연결 변경 시 화면을 닫고 작업마다 report와 연결을 다시 검증한다.

전체 회귀 172개, source/test typecheck와 build가 통과했다. 제출 검사 6개는 실제 TLS fixture와 공유 queue로 확인한 hash·재전송·403/503·disconnect·보고서 소유권·snapshot·local candidate를 검증한다. VS Code 1.135.0의 source checkout과 최소 버전 1.90.2의 최종 VSIX에서 실제 command→연결 선택→미리보기→확인→보류→화면 재개→local candidate→전송→접수증→설정 변경 시 닫기를 검증했다. 합성 리뷰를 사용했으며 실제 모델 호출과 운영 서버 변경은 0회다. 두 native host의 종료와 task-owned OS credential·암호화 profile·fixture 정리를 확인했다. Native screenshot은 일부 잘린 이미지이며 전체 시각 검증 근거로 삼지 않는다.

VSIX SHA-256은 `6baec4e599408dc4bff6dec689591e8702135afc60834eb482575afb65cea3a0`다. 소스를 push하고 기존 2.3.0 설치본을 백업한 뒤 사용자 VS Code에 2.4.0을 설치했다. 설치된 실행 bundle·service manifest와 검증 VSIX의 hash가 일치한다. 사용자 창의 reload는 강제하지 않았다. Bundled CLI는 alpha.17을 유지하며 전역 CLI를 교체하지 않았다.

[제출 화면·검증·설치 증거](evidence/P08-CD-review-submission.json)를 따른다. 이번 전달은 C05의 client 부분이며 중앙 intake 검토·후보 전환·권한자 승인·승인 상태·새 bundle sync·실제 재리뷰 순환은 아직 남아 있다. 이 상태를 C05 전체 완료로 집계하지 않는다. P08-C04/C06과 이전 phase 잔여 조건, P09 출시 및 P10–P13을 포함한 전체 goal을 계속 유지한다.

### C05 중앙 intake 검토와 후보·요청 연결

웹 리뷰 기준 화면에 클라이언트 제출 목록과 검토 처리를 추가했다. 현재 DB의 사용자·tenant membership·repository grant·criteria role로 열람/관리 권한을 확인하며 client bearer는 관리 API에서 받지 않는다. 원문 payload hash 확인 후 종결, 유지관리자가 작성한 기준 후보 등록, 기존 기준의 정정·예외 요청 연결 중 하나를 저장한다. 트랜잭션과 입력 hash로 같은 요청의 중복 후보 생성을 막으며 다른 처리는 conflict로 반환한다.

채택한 기준은 draft로 시작한다. 결과 건수만 제출한 항목은 기준으로 전환할 수 없다. 예외 연결에는 적용 범위와 기간이 필요하며 보완한 요청의 작성자는 curator로 기록한다. 같은 사람이 owner 역할도 갖더라도 자신의 예외 요청을 승인할 수 없다. 기존 평가·관찰·활성화/owner 승인 조건은 그대로 적용한다. 원본 제출·intake decision은 30일 보관하되 채택한 메시지와 client-reported 출처는 기준/요청 이력에 보존한다. 화면에서 이 보관 차이를 확인할 수 있다. 새 DB migration은 `0044_review_submission_intake.sql`이다.

실제 격리 PostgreSQL의 criteria 통합 24개와 client-credentials 통합 12개, 웹 테스트 119개, runtime/web typecheck·build 및 전체 lint를 통과했다. Chrome에서 제출을 후보로 채택하고 연결된 draft를 확인했으며 기존 평가·승인·예외·수정·퇴역 경로도 통과했다. 초기 보완 검사에서 기존 독립 승인 사례에 잘못 추가한 자기 승인 기대값을 제거하고 제출 처리 select의 접근 가능한 이름을 명시했다. 전체 lint가 생성 artifact까지 검사하던 설정과 기존 Node process fixture의 globals 범위도 수정했다. 모델 호출은 없었다.

PRISM-DEV의 기준 배포는 Helm 55·alpha.44·migration 43임을 확인했다. 기존 리소스/DB fingerprint와 암호화 pg_dump를 확보했으며 alpha.45·chart 0.10.42 배포 검증을 이어간다. 이 source checkpoint만으로 배포나 P08-C05 전체 완료를 선언하지 않는다.
