# API key No expiration

프로필 → 클라이언트 연결 → 새 API key의 만료 설정에 **No expiration (만료 없음)**을 추가했다. 기본값은 기간 지정 30일이며 1–90일 입력을 유지한다. 기간 설정을 바꿔도 입력한 일수를 보존하고 무기한 선택에서는 일수 입력란을 숨긴다. 목록은 Invalid Date 대신 만료 없음을 표시한다. 기존 key의 만료일은 바꾸지 않는다.

`lifetimeDays: null`이 명시적인 무기한 요청이고 발급·목록·bearer identity는 `expiresAt: null`을 반환한다. Migration 0059는 NOT NULL만 제거한다. 기존 timestamp와 날짜 key의 양수 만료·90일 상한 DB 제약을 보존한다. 무기한 key도 50개 한도에 포함하고 폐기, 현재 계정·grant·credential epoch·비밀번호 변경·SAML freshness 검사를 그대로 적용한다. 지식 manifest의 5분 온라인 freshness와 서명된 offline lease는 늘리지 않았다.

UI는 `reference-led-frontend`와 agent-skills의 프런트엔드 가이드를 적용했다. 실제 기존 프로필의 client/repository select와 같은 native select·label·fieldset을 재사용했다. 별도의 카드나 디자인 시스템은 추가하지 않았다.

## 검증과 배포

- GCR 관련 113개 통과, 기존 Windows 전용 1개 제외. 계약, 실제 PostgreSQL 발급·조회·철회·50개 제한·날짜 경계·권한/비밀번호 차단, HTTPS 연결과 캐시 회귀를 포함한다. TypeScript 포함 전체 build, 변경 파일 lint·formatter와 Linux amd64 이미지 검사가 통과했다.
- 최초 묶음 실행의 두 실패는 새 테스트의 CLI 명령 누락과 이미 만료된 manifest fixture에 대한 성공 가정이었다. 명령을 고치고 무기한 key 접근 검사는 독립적인 reader repository API로 분리했다. 관련 묶음 전체를 다시 실행해 통과했다. 만료된 manifest 재사용을 허용하는 제품 수정은 하지 않았다.
- 실제 frontend build를 합성 HTTP API에 연결한 in-app browser에서 선택·발급·목록 재조회·폐기와 일수 45 보존을 확인했다. 420×760에서 가로 넘침이 없다. 기존 Chrome 프로필에는 작성 중인 key 이름이 있어 그 탭을 새로고침하거나 발급하지 않았다.
- PRISM-DEV 앱 **0.8.0-alpha.79**, chart **0.10.75**, Helm revision **87**, deployed. Server·worker·sandbox Ready, Helm 연결 시험 Succeeded. HTTP와 HTTPS health·asset 해시 대조 및 인증 없는 profile/key API 401 확인.
- HTTPS 확인의 첫 Node 실행은 개발 CA가 신뢰 목록에 없어 실패했다. 기존 배포의 development CA 공개 인증서를 corporate CA와 함께 해당 검증 프로세스에만 지정해 재검사했다. 검증을 끄거나 새 인증서를 발급하지 않았다. DB는 verify-full / TLSv1.3를 유지했다.
- 17개 테이블 전체 행 해시와 기존 migration checksum이 같고 0059만 추가됐다. Secret·ConfigMap·PVC·HTTPRoute·identity release와 기존 사용자 설정이 보존됐다. 운영 key는 새로 발급하거나 연장하지 않았다.

## 클라이언트 호환성

공통 client-contract alpha.49 / client-core alpha.50 / client-executors alpha.51과 GCR CLI alpha.40을 고정 artifact로 만들었다. 기존 날짜 key 연결은 유지한다. 이전 nullable expiry 미지원 클라이언트에는 무기한 key가 연결되지 않으므로 갱신한 클라이언트를 사용한다.

Commit Defender **2.13.1**에 새 공통 package와 service를 포함해 로컬 설치했다. 새 core로 무기한 key 연결·원문 조회·유한 캐시 lease·철회 후 offline 차단을 검사했고 관련 CD 테스트 24개와 source/test TypeScript 검사가 통과했다. macOS package에는 Windows helper가 새로 컴파일되지 않으므로 기존 Windows 빌드 1.0.3을 source·artifact·실행 파일 해시와 대조해 재사용했다. CD/내장 service 양쪽에 동일한 helper를 포함했다. Windows OS 코드는 변경하지 않았다.

CD build source는 `c6fc899d03ead0491a051e1c879e8a98cd2f7490`, compiled bundle commit은 `976a0bea019822eb2361c6e2bc8118b70062cbb3`다. VSIX SHA256은 `6d9a953087c5d647028a2c1fdcb9ebb30edfb18828ff9053fcf8a799a3c8eb65`이며 설치 파일들과 byte 단위로 같다. 기존 사용자 설정 해시도 같다. 이미 열린 사용자 Extension Host의 적용 상태는 확인하지 않았고 강제 reload는 하지 않았다. VS Code를 다시 불러오면 갱신 버전으로 연결할 수 있다. Marketplace와 전역 CLI 설치는 진행하지 않았다. 새 Windows/Linux Host 검사는 하지 않았고 macOS standalone CLI artifact는 Windows helper 배포를 대신하지 않는다.

프로필을 새로고침해 만료 없음으로 새 key를 발급한 뒤 기존 연결 절차대로 클라이언트에 입력한다. 기존 key를 무기한으로 자동 변환하지 않는다. 원문은 발급 시에만 확인할 수 있고 같은 목록에서 폐기한다.
