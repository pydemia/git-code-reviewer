## 구현

GCR `windows-service-pipe.ts`와 native helper에 Windows named pipe를 추가했다.
pipe 이름은 사용자 SID·profile·데이터 디렉터리의 NTFS file identity로 정한다.
대소문자 별칭은 같은 디렉터리로 연결하고 별도 디렉터리는 분리한다.
생성 시 current-user 전용 보호 DACL, 첫 instance 독점, 원격 접속 거부를
적용한다. client는 데이터를 쓰기 전에 server process SID를 확인한다.
JSON frame 한도와 연결 한도를 적용하고 client ACK 뒤에 연결을 닫는다.

참조한 Windows 명세는
[Named Pipe Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)와
[CreateNamedPipeW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createnamedpipew)다.

기존 encrypted CAS service ownership과 repository/profile 인가를 유지했다.
소유 Node가 종료되면 pipe helper도 종료한다. 중단 작업은 성공으로 바꾸지
않으며 저장 완료가 확인된 결과만 복구한다. Unix socket 분기는 유지했다.

native `replace-private`/`remove-private`는 ACL·reparse 검사를 거친다.
파일 교체는 private 임시 파일의 flush와 원자적 rename을 사용한다.
CD `windowsPrivateFiles.ts`가 hook state·lock·게시를 이 경로로 연결한다.
service와 advisory 프로그램은 본문·helper·manifest hash를 함께 사용한
private 디렉터리에 저장하며 설치 후 bytes를 다시 대조한다.

CD는 Windows PATH에서 native `.exe`를 찾고 service를 `shell:false`와
숨겨진 창으로 실행한다. Git for Windows의 managed hook은 native Node
advisory로 전달한다. 기존 hook의 shebang 실행은 Git의 `hook run`에 맡겨
stdin·종료 상태·원본 파일을 보존한다. 이 Git 진입점과 Codex의 native
실행 경로는 별개다. legacy Python hook 기능을 확장하지 않았다.

## 기존 trigger 범위

모든 trigger의 opt-in 기본값은 false다. repository 설정만으로 실행 권한을
만들 수 없으며 사용자 또는 명시적 private worktree 설정을 사용한다.
사용자 작업 저장소의 자동 리뷰는 켜지 않았다.

| Trigger | 기존 입력과 실행 | 확인한 동작 |
| --- | --- | --- |
| Save | 편집기의 명시적 저장, working-tree snapshot | Auto Save·typing·동일 저장 제외, source hash 고정 |
| Stage | 실제 index 변경, index snapshot | unstage/no-op 제외, Host 종료 후 관찰·재개 |
| Commit | Git managed pre-commit, index snapshot | Stage와 동일 source 중복 억제, 원래 hook 유지 |
| Push | Git managed pre-push, commit-tree snapshot | 원래 stdin 보존, 로컬 bare remote에서 검증 |

수동 리뷰 우선순위, 보류·재개, 최소 간격·시간당 한도, 취소 소유 관계,
서비스 장애 시 다른 모델로 대체하지 않는 동작을 유지했다. partial·failed·
interrupted는 completed로 합치지 않는다. W02의 unknown-read-id 오류 처리를
변경하지 않았다.

## 실제 모델 리뷰

[호출 전 계획](evidence/W03-real-review-plan.json)에 trigger, source/base/caller,
동작 규칙과 경계값 테스트, 기대 report·저장 결과, Host·service·worker hash,
기존 계정의 `gpt-5.6-luna / high` 1회·240초 한도를 기록했다.

별도 Windows ARM64 Extension Host에서 설치된 VSIX 2.12.4를 로드했다.
임시 한글·공백 경로 저장소에서 `sum.ts`의 덧셈을 뺄셈으로 바꾼 index를
고정했다. `consumer.ts`가 호출하며 `[2,3] → 5`와 `[] → 0`이 동작 규칙이다.
검증 runner가 실제 테스트를 먼저 실행해 비어 있지 않은 입력의 실패와
빈 입력의 통과를 확인했다. 모델이 테스트 source를 읽는 것은 실행이 아니다.

첫 호출은 service가 `completed`, exitCode 1을 반환했지만 검증 harness가
exitCode 0을 요구해 report 본문 확인 전에 실패했다. 기존 CLI에서 1은
결함 발견을 나타낸다. 임시 profile 정리로 본문이 남지 않아 이 호출을
성공으로 집계하지 않았다. [첫 기록](evidence/W03-native-host-attempt1.json).

제품 실행 코드는 변경하지 않았다. report를 먼저 보존하고 상태·오류·근거와
기존 `reviewExitCode(report)`를 함께 확인하도록 harness를 고쳤다. 정리 경로의
slash 비교도 수정했다. [추가 호출 계획](evidence/W03-real-review-retry-plan.json)에
동일 artifact로 추가 1회·240초, 누적 최대 2회와 재검증 범위를 기록했다.
자동 재시도는 없다.

[두 번째 실제 리뷰](evidence/W03-native-host-attempt2.json)는 64.217초 만에
완료됐다. `report.status=completed`, problems 0건, 검증된 source 2행의
P3 결함 1건이며 base·caller·테스트를 근거로 뺄셈 오류를 지적했다. 빈 배열은
기존 결과 0을 유지한다는 반증도 확인했다. 모델 응답은 테스트를 읽었으며
실행하지 않았다고 명시했다. source hash 고정과 암호화 history의 동일 결과
재조회, history refresh, 정지 시 hook·grant 복원을 확인했다.

이 호출의 모델 report 검증은 통과했지만 바깥 Host 실행기는 service가 남은
종료 단계에서 `cleanup-failed`를 반환했다. 전체 launcher 실행을 성공으로
표시하지 않는다. 이후 소유 service·관찰한 자식 process가 모두 종료됐고
임시 profile·key가 제거된 것을 확인했다. 정확한 native cleanup 내부 실패
지점은 기록되지 않았으며 persistent service를 Host보다 먼저 정지하지 않은
검증 순서가 관찰된 차이다.

[수명 재검증 계획](evidence/W03-lifecycle-retest-plan.json)에 모델 추가 호출
0회를 기록하고 시험 Host가 자신의 service를 먼저 stop한 뒤 종료하도록
harness를 수정했다. [실제 Host 수명 검사](evidence/W03-native-host-lifecycle.json)는
modelCalls 0, service 정상 종료, launcher code 0/error 없음, 임시 profile·
key·fixture 삭제로 통과했다. 두 번째 report와 별개의 검증이다. 실제 모델
호출은 누적 2회, 내용·근거·저장 재조회를 확인한 완료 report는 1건이다.
[process 정리 확인](evidence/W03-process-cleanup.json)에서 관찰한 소유 process의
잔존은 0개다. 제품 실행 코드와 고정 artifact는 재검증 중 바뀌지 않았다.

service review worker는 private CLI의 Node process 안에서 실행된다.
VSIX의 standalone worker hash도 연결했지만 이 service 호출이 별도 standalone
worker process를 사용했다고 표시하지 않는다. 중앙 연결·업로드는 없었다.

## 사용·해제·복구

사용자는 원하는 시점에 VS Code를 재시작하거나 Reload Window를 선택해
새 설치를 적용할 수 있다. `Commit Defender: Automatic Reviews`에서 현재
repository/profile의 원하는 trigger만 opt-in한다. serviceNodePath는 native
Node `.exe`를 사용한다. `.cmd` wrapper나 WSL 경로를 모델 실행 경로로 쓰지 않는다.

일시 정지는 `automaticReviewsPaused`를 사용한다. trigger 해제 시 이 확장이
보유한 grant와 managed hook 연결을 제거하고 기존 hooksPath를 복원한다.
사용자가 이후 수정한 hook·설정은 덮어쓰지 않는다. 기존 legacy hook 설치
명령을 managed 자동 리뷰 설정과 혼동하지 않는다.

중단 결과는 `Commit Defender: Recover Background Review`에서 확인한다.
이 명령은 저장된 완료 결과를 대조하며 모델 리뷰를 새로 실행하지 않는다.
저장 완료가 없으면 interrupted를 유지한다. 구버전 service가 실행 중이면
설치된 VSIX와 다른 버전일 수 있으므로 process의 프로그램 hash를 먼저 확인한다.
이 작업에서는 시작 시 사용자 service가 없었고 시험 profile만 기동·종료했다.
사용자 service를 자동으로 종료·교체하지 않는다. 명시적으로 자신의 profile
service를 정지한 뒤 새 버전으로 기동해야 한다.

## 정리와 제한

[보존 검사](evidence/W03-preservation.json)에서 사용자 VS Code 설정, Codex
config/AGENTS와 Codex CLI hash가 시작 때와 같았다. auth 파일은 존재하며
hardlink 수는 1이다. 임시 검증 계정은 0개이고 사용자 저장소의 hook bytes와
설정도 유지됐다. 다른 작업의 process·container를 종료하지 않았다. [정리 차단 목록](evidence/W03-cleanup-blocked.json)의 실패 fixture
18개와 첫 실제 검증 Host 폴더는 실행 도구의 자동 승인 검토가 재귀 삭제를
`blocked by policy`로 거절했다. 상세 사유는 제공되지 않았다. 다른 도구로
우회하지 않았으며 정확한 경로를 수동 정리 대상으로 남겼다. 첫 Host의
service 종료와 3개 임시 private profile 경로 부재는 확인했다.

W04, Marketplace 게시, PRISM 배포·운영 변경, 새 수집·PR·댓글·중앙 업로드,
서버 모델 대행과 provider framework 확장은 수행하지 않았다.
