## 연결 확인

기록된 서버는 `https://pr-review.prism.ai`다. 이 Windows PC의 DNS는
해당 이름에 NXDOMAIN을 반환했다. 기존 배포 문서의 `10.250.107.189:443`에
공개 development CA와 원래 hostname을 유지한 요청도 5초 연결 제한에서
timeout이었다. 인증서 검증을 끄거나 hosts/서버 설정을 변경하지 않았다.
기본 Windows CD 데이터 경로에 중앙 연결 저장소는 없었다. 기존 접속
경로와 reader 연결 준비 위치를 사용자에게 확인하고 독립 작업을 계속한다.

## 실제 호출 전에 고정한 사례와 한도

CD의 `test/helpers/g04-fixtures.mjs`를 재사용한다. schema·service·API
호출부·repository 동작 규칙·경계값 테스트·Pydantic 2 의존성 선언을
고정한다. 사용자 저장소에 시험 결함을 만들지 않는다.

| 사례 | 변경 | 기대 판단 |
| --- | --- | --- |
| defect | model_validator를 미호출 자유 함수로 옮김 | reference_id 누락/null이 model_validate 호출 경로에서 거절되지 않는 결함과 과거 지침의 관련성을 설명 |

| unrelated | 정상 schema를 유지하고 service에서 DB archived 상태 거절 | DB 상태 검사를 schema로 옮기라고 요구하지 않으며 지침의 제외 조건을 설명 |

기존 기본 Codex 계정의 `gpt-5.6-luna / high`를 사용한다. 초기 한도는
각 사례 1회, 총 3회, 회당 최대 240초다. 아직 실제 모델 호출은 0회다.
대체 모델은 임의로 선택하지 않는다. 실패 후 추가 호출에는 원인·수정·
재검증 대상·추가 횟수/timeout을 먼저 기록한다.

온라인 manifest의 기존 5분 수명과 signed offline lease를 유지한다.
모델 호출 전 잔여 수명이 준비·실행 한도를 충족하는지 확인하고 그렇지
않으면 정상 재동기화 또는 이미 승인된 유효 offline 경로를 사용한다.
자료 제공 metadata와 모델 본문의 출처·적용/충족/제외 설명은 따로 평가한다.
timeout/partial/실패는 완료 사례가 아니며 읽은 테스트는 실행으로 집계하지
않는다. 실제 reader 요청은 GET과 서버 소유 ID/cursor/revision으로 제한한다.

## 로컬 HTTPS 검증으로 변경한 실행 경로

사용자는 이 PC에서 PRISM-DEV에 접근할 수 없으며 로컬 서버로 시험해야
한다고 확인했다. 실제 PRISM-DEV의 현재 원문·revision 대조는 불가능하다.
로컬 검증만으로 완료 기준을 변경할지는 별도로 확인 중이다.

G02-guidance-draft와 G04-guidance-state의 지침 내용을 재사용한다. 로컬
HTTPS publisher는 새 서명 key·검증용 reader·cache를 사용한다. 원문과
답글 전체가 기록에 없으므로 명시적으로 재구성한 본문을 사용하고 실제
원문의 hash와 다른 로컬 hash를 기록한다. #915는 기록된 PR ID로 빈
uncollected 응답을 제공하며 실제 중앙 자료 없음으로 해석하지 않는다.

세 사례 모두 모델 호출 전에 원문·답글·본문 버전·관찰·지침 응답을 GET으로
읽고 암호화한 cache의 signed offline lease로 고정한다. 온라인 manifest는
기존 5분 이내이며 유효기간을 늘리지 않는다. 최초 호출 한도는 그대로
3회(각 240초)다. 각 Host에서 1회만 호출하고 자동 재시도하지 않는다.
검증 모델은 기존 계정의 gpt-5.6-luna/high다.

고정 fixture는 CD test/helpers/g04-fixtures.mjs다. source/base뿐 아니라
service의 update_block/preview_block, api의 update_endpoint/preview_endpoint,
DB repository의 동작 규칙, 누락/null/유효 reference_id와 archived 경계값
테스트, Pydantic 2 의존성 선언을 제공한다. pytest는 실행하지 않으며
모델이 읽은 테스트를 실행 증거로 집계하지 않는다.

설치된 2.12.3 worker를 그대로 실행하며 검증용 wrapper는 native process
요청·종료의 비식별 metadata만 관찰한다. stdin, prompt, credential과 모델
원문 stream을 기록하지 않는다. 결과 report는 재구성 fixture 검증 자료다.
중앙 GET 경로·query 이름·body byte 수와 provider 실행 관찰을 분리한다.

첫 로컬 Host 준비는 v2 memory의 aggregationKey 누락으로 중단됐고,
수정 후 두 번째 준비는 관찰 응답에 message 전용 필드가 포함되어 엄격한
스키마 검증에서 중단됐다. 두 건 모두 모델 호출은 0회다. fixture를 수정한
뒤 9종 reader 응답 decode, TLS publisher 시작과 typecheck를 먼저 통과했다.
추가 모델 한도는 쓰지 않으며 최초 defect 1회/240초를 다시 준비한다.
검증용 TLS private key도 이후 시험에서는 openssl 출력 pipe에만 보유한다.

## Windows 저장 경로 수정과 회귀

alpha.47에서 중앙 snapshot 동기화가 기존 60초 제한을 넘었다. native
helper를 파일 연산마다 시작하는 비용이 원인이었다. 제한 시간을 늘리는
대신 helper 1.0.2에 제한된 저장 session을 추가했다. Node process/worker별
pipe에서 요청을 직렬화하고 queue 64개, 합계 36 MiB, 요청 deadline 15초를
유지한다. 100 ms idle 또는 소유 process 종료 시 helper가 종료된다.
process/auth-link 실행은 이 저장 session에서 허용하지 않는다.

각 연산은 기존 NTFS ACL·reparse·handle 검사를 다시 수행한다. 인증·권한을
cache하지 않는다. 진행 중 publish의 취소는 commit-unknown으로 유지하며
후속 요청은 새 session에서 처리한다. 기존 Job Object 기반 모델 실행과
취소·timeout·후손 정리는 변경하지 않았다.

client 0.1.0-alpha.48을 새 고정 artifact로 만들고 CD 2.12.3에 포함했다.
기존 artifact는 덮어쓰지 않았다. private service alpha.37은 재사용한다.

[회귀 근거](evidence/W02-regression.json)의 최종 GCR 두 묶음은 72건과
65건, 총 137건 통과·실패 0건이다. 실제 Windows credential 저장 후 별도
Node process의 재조회, NTFS/reparse/snapshot, 저장 session의 취소·소유
process 종료·원자성, TLS/CA/pin/redirect, scope·철회·만료·오류 분류와
Codex 격리 회귀를 포함한다. macOS/Linux는 adapter 모의 검사이며 해당
OS의 native 실행 성공으로 표현하지 않는다. 전체 suite 실행은 아니다.

CD는 고정 alpha.48 consumer 검사 22건, 중앙 리뷰 합성 회귀 12건,
history 2건을 통과했다. Windows Host 합성 사전 검증에서는 실제 native
credential/cache와 설치 worker 준비를 확인했고 모델 호출은 없었다.
해당 Host의 연결 준비 시간은 1714 ms였다. 이 수치는 단일 관측이며
일반적인 성능 보장으로 해석하지 않는다.

## 실제 모델 응답과 저장 결과

[세 사례 수용 근거](evidence/W02-model-acceptance.json)는 초기 한도 3회만
사용했다. 모델은 기존 기본 Codex 계정의 gpt-5.6-luna/high, 각 240초다.
추가 모델 호출·timeout·partial·모델 실패는 0건이며 3건 모두 completed다.

| 사례 | Host 측 실행 시간 | 결함 수 | 실제 응답에서 확인한 판단 |
| --- | ---: | ---: | --- |
| defect | 84.554초 | 1 | 미호출 자유 함수 때문에 두 model_validate 진입점에서 reference_id 누락/null을 허용한다고 지적하고 지침 ID·출처 URL을 인용 |
| fixed | 97.859초 | 0 | validator가 두 service 진입점에서 실행되며 과거 지침이 이미 충족됐다고 설명 |
| unrelated | 65.889초 | 0 | archived 저장 상태 검사와 기존 요청 값 검증을 구분하고 repository·caller 동작을 근거로 현재 변경을 인정 |

무관 사례의 표현은 지침을 문자 그대로 `excluded`라고 분류하지 않고
기존 요청 값 검증은 충족됐으며 새 archived 검사는 이를 바꾸지 않는다고
설명했다. `files[].summary`는 저장된 DB record와 repository/caller를
근거로 들었다. DB 검사를 schema로 이동하라고 요구하지 않았다.

수용 판단은 모델이 작성한 summary·file summary·finding을 직접 읽고
평가했다. context.entries 및 core가 붙인 reasoning 출처는 자료 전달
metadata이며 모델 판단 자체의 증거로 계산하지 않았다. 세 응답 모두
테스트를 실행하지 않았다고 명시했다. pytest 실행 성공 주장은 없다.

각 Host의 reader 요청은 16회, GET만 사용했고 request body는 0 byte였다.
모델 실행 중 중앙 요청은 0회였다. provider 경계에서는 각 1회의 account
review와 2회의 loopback catalog probe를 별도로 관찰했다. request/stream
원문은 저장하지 않았다. 이 관찰은 CLI 실행 경계이며 provider 네트워크
payload의 packet capture는 아니다.

세 결과 모두 암호화 저장 후 다시 읽은 report가 원래 결과와 같았다.
설치 확장의 showHistoryEntry 명령으로 저장 결과 표시를 열었다. 해당
Host의 temporary profile/key/reader credential/session/process는 정리했다.

[artifact 연결](evidence/W02-artifact-linkage.json)과
[VSIX 내용 대조](evidence/W02-vsix-contents.json)에 전체 hash를 남긴다.

이후 test harness·문서 commit은 설치된 실행 코드를 바꾸지 않는다.

- client: 0.1.0-alpha.48, native helper: 1.0.2
- VSIX: commit-defender-2.12.3-win32-arm64.vsix

2.12.3은 로컬 extension registry와 설치 파일에서 확인했다. VSIX와 설치된
extension/worker/helper/service hash가 모두 일치한다. 실제 검증 Host는
별도 임시 user-data/shared-data 경로의 VS Code 1.137.0 ARM64,
Node 24.18.1이다. 사용자 Host는 강제 재로드하지 않았고 적용 버전은 미확인이다.

사용자가 확장을 다시 활성화한 뒤 현재 worktree/profile에서
`Commit Defender: Central Review Connection`을 연다. 기존 신뢰할 수 있는
연결 JSON을 고르고 public signing-key fingerprint를 확인한 다음 reader
key를 password 입력에 넣는다. JSON에 key를 넣지 않는다. `Connection
status`에서 사용자·저장소·hash·만료를 확인하고 `Synchronize knowledge`,
`Browse PR review history`, `View downloaded review knowledge`를 사용한다.

수동 리뷰는 `Analyze Staged Files` 또는 `Analyze Current File`을 사용한다.
필요할 때만 해당 worktree의 `Use signed offline knowledge`를 선택한다.
lease 만료·철회 이후에는 기존 cache를 재사용하지 않는다. History에서
저장 결과를 열어 source/context hash와 출처를 확인한다. 전역 provider,
모델·자동 실행 설정과 CLI는 변경하지 않았다.

## 제품 reader 라우트의 로컬 서버 검사

[제품 reader 근거](evidence/W02-product-reader.json)는 합성 응답 publisher와
별도다. GCR의 registerAuthentication, client credential, review-history,
review-knowledge, 지침 활성화·publication·signing 코드를 사용했다. Windows
Node에서 실제 HTTPS listener와 client-core를 실행했다. PostgreSQL만 로컬
Docker Desktop Linux ARM64 container에서 실행했으며 이 DB 실행을 Windows
네이티브 검증으로 집계하지 않는다. 외부 서버·운영 DB는 사용하지 않았다.

일반 reviewer의 knowledge:read key로 #917/#915 조회, 원문 재현 자료,
답글, 본문 버전, observation, 활성 지침을 읽고 offline 재조회와 비교했다.
실제 publication bundle에 활성 지침이 포함됐으며 지침 본문은 G02 기록과
일치했다. 로컬 생성 ID·원문 hash는 역사적 ID·hash와 따로 기록했다.
온라인 manifest 수명은 정확히 5분이며 signed offline lease는 1시간이었다.

HTTP는 GET 15회, body 0 byte였다. 권한 없는 다른 로컬 저장소 ID는
403 CLIENT_SCOPE_DENIED였다. 별도로 발급한 검증 key의 유효기간만 줄여
만료시킨 요청은 401 CLIENT_AUTHENTICATION_REQUIRED였다. 서버는 만료와
알 수 없는 credential을 같은 인증 오류로 표현하므로 만료 원인은 해당
검증 key의 DB 상태로 확인했다. 유효기간을 늘리거나 만료 key를 되살리지
않았다. 검증 key 철회 후 동기화와 offline cache 사용이 거부됐다.

첫 DB 준비는 initdb의 기본 localhost HBA가 Docker bridge의 Windows
client를 허용하지 않아 28000으로 실패했다. 로컬 전용 container의 시험
DB·role에 SCRAM 인증을 요구하는 HBA를 설정했다. 이후 fixture SQL의
동일 parameter에 서로 다른 타입을 추론한 42P08은 명시적 int cast로
수정했다. 모든 시도의 container·volume·임시 profile/key는 정리했다.
이 오류들은 제품·모델 실패와 별도이며 추가 모델 호출은 없었다.

DB password는 initdb stdin으로만 전달했고 SCRAM hash만 DB에 저장했다.
TLS·서명 private key, reader key, bootstrap password, session은 memory와
기존 OS 보안 저장 경로에서만 취급했다. credential을 argv·환경변수·평문
임시 파일로 전달하지 않았다. startup signing-key 경로 설정은 파일을
읽는 server 전체 launcher 대신 memory KeyObject를 전달하는 테스트
구성에서 사용됐으며 TLS·서명·reader 인증은 실제 구현으로 검증했다.

재현 명령은 `node apps/runtime/node_modules/tsx/dist/cli.mjs
apps/runtime/test/windows-local-reader-probe.ts`다. Git OpenSSL의 실행 경로가
현재 process PATH에 있어야 한다. Docker Desktop local named pipe와
기록된 고정 PostgreSQL image만 허용한다. 기존 사용자 DB나 volume을
선택하지 않는다. 결과는 tmp/w02/W02-product-reader.json에 기록된다.
